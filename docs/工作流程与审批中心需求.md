# 工作流程与审批中心需求

## 1. 建设目标

建立统一的工作流程模型，将系统中的正向业务流程和逆向业务流程纳入同一套流程框架。流程模型负责定义业务对象、流程方向、处理方式、执行范围、用户节点、状态校验和通知规则；流程实例和流程任务负责记录每次实际运行过程。

逆向操作只是工作流程中的一类。第一阶段接入正向自动流程并准备逆向模型；“所有逆向操作必须审批”的业务约束从第二阶段逆向接口切换上线时才生效。后续可通过流程模型扩展其他处理方式。

## 2. 流程方向与处理方式

每个流程模型必须配置以下属性：

| 属性 | 说明 |
|---|---|
| 流程名称 | 例如合同创建、订单配货、发货撤回 |
| 流程方向 | 正向、逆向 |
| 业务对象 | 合同、订单、机台、库存、客户成品、基础资料等 |
| 处理方式 | 自动通过、需要审批 |
| 执行范围 | 整单、单机台、批次、合同或基础资料对象 |
| 状态校验 | 执行前必须满足的业务条件 |
| 节点配置 | 发起、审批、执行、通知等用户节点 |
| 版本状态 | 草稿、已发布、停用 |
| 版本号 | 保证历史流程实例继续使用创建时的规则 |

正向流程首期全部采用自动通过。自动通过仍然需要生成流程实例、执行记录和审计日志，不能绕过流程追踪。

首期逆向流程统一设置为“需要审批”，不得绕过审批直接执行。后续如需开放自动通过，必须由已发布流程模型明确配置并经过权限控制。

正向必需流程模型不允许停用唯一可用的已发布版本。业务提交时若不存在可用的已发布模型或模型配置无效，后端必须明确报错并禁止业务提交，不能在没有流程记录的情况下继续执行。

## 3. 首期正向流程

首期纳入以下正向自动流程：

- 创建合同；
- 合同提交并进入后续业务环节（仅在核实存在独立提交动作后作为独立主流程）；
- 创建销售订单；
- 订单配货；
- 成品入库；
- 库位转移；
- 发货确认；
- 客户成品登记（仅在核实存在独立写入动作后作为独立主流程）和客户机台规划。

正向流程的通用路径为：

```text
发起业务操作 → 系统校验 → 自动通过并记录 → 自动执行 → 同事务更新业务数据和流程实例 → 生成派生任务 → 提交后按配置发送通知
```

正向流程首期即接入现有业务操作。所有正向操作虽然自动通过，仍必须创建流程实例、自动通过审批记录、执行记录和审计日志；审批人记为系统账号，执行人记录实际操作账号或系统账号，不将自动通过记作人工审批。

每个正向流程必须补充以下业务定义：

| 定义项 | 内容 |
|---|---|
| 触发接口 | 实际触发该正向业务操作的后端接口或业务入口 |
| 前置状态 | 允许操作的业务对象状态和必要条件 |
| 目标状态 | 操作成功后业务对象应达到的状态 |
| 派生动作 | 操作成功后自动生成的关联记录、库存变化或后续任务 |
| 失败结果 | 操作失败时业务数据保持的状态、失败尝试记录及用户可见结果；事务回滚时不生成成功主实例 |
| 是否需要通知 | 明确是否在事务提交后发送通知 |

正向业务变更与成功的流程实例、自动通过记录和核心执行记录在同一数据库事务中提交；任一写入失败，业务变更与该实例整体回滚，不得出现业务成功而流程记录缺失。事务回滚后的失败尝试由独立的审计记录留痕，不能伪装成已提交的成功实例。正向流程失败默认不发送通知，只保留失败记录；成功后的通知按模型配置在事务提交后发送。

逐项正向流程的触发接口、前置状态、目标状态、派生动作、失败结果和通知设置尚待对照现有业务代码填写，不能仅以页面示例数据作为接口清单。

正向流程逐项对照时以现有真实业务入口和状态规则为准，不因接入流程记录而改变现有业务行为。按实际业务单据各生成一个主流程实例；一次请求涉及多张单据时，各实例共享同一个请求批次号，并分别关联各自的业务单据。同一单据的同一次独立业务提交动作只生成一个主实例；多个页面入口或内部函数调用同一业务动作时不得重复生成。该动作产生的库存变化、关联记录和后续任务作为对应主实例的派生动作关联记录。合同提交若有独立改变合同状态的提交动作，应生成独立主实例；若只是创建合同后的结果，则归入创建合同实例的派生动作。客户成品登记若有独立写入动作，同样生成独立主实例；若由发货自动产生，则归入发货确认实例的派生动作。须先核实真实入口，不得仅凭页面或流程名称创建主实例。上述六项定义逐项核实后，才可认定对应正向流程完成接入。

每项正向流程需建立“页面名称、数据库原始状态值、后续允许操作”的映射，并列明触发前后各核心对象的原始状态值。流程实例同时保存原始状态值和展示名称；状态校验以原始值为准，不以页面文案判断。`active`、`ready`、`allocated`、`packed`、`done` 等现有值须逐入口核实，不在核实前直接认定为统一流程状态。

## 4. 首期逆向流程

首期逆向操作范围：

- 取消合同；
- 删除机型字典；
- 删除订单；
- 撤回配货；
- 发货撤回；
- 客户成品中核销发货撤回。

逆向操作默认按流程模型配置执行。需要审批的逆向流程执行以下规则：

- 按配置的业务范围执行，整单流程必须按整单处理；
- 审批通过后自动执行；
- 审批期间订单、机台、合同、库存或配货状态发生变化时，整单执行失败并记录原因；
- 已存在未完成逆向流程的业务对象，不得重复发起相同类型流程；
- 执行失败时不得显示为成功，必须进入执行异常或待人工处理状态。

首期所有逆向流程均需要审批。审批通过后自动执行；审批期间不允许修改本次流程的业务范围，不允许临时增删机台。

整单单位以用户实际发起的业务单据为准。发起时必须保存业务对象清单和状态快照，审批通过时重新校验全部核心对象；任何一个对象不满足条件，整单失败，不允许部分执行。

首期逆向操作的结果规则：

| 操作 | 审批通过后的目标结果 |
|---|---|
| 取消合同 | 按合同整单取消，采用软删除或可恢复状态 |
| 删除机型字典 | 采用软删除；存在有效业务关联时禁止删除 |
| 删除订单 | 按订单整单处理，采用软删除；存在不允许删除的关联状态时整单失败 |
| 撤回配货 | 订单回到“待配货”，原配货记录改为“已撤回”并保留历史，相关机台恢复为“待入库” |
| 发货撤回 | 发货单标记为“已撤回”，订单回到“待配货”，原配货记录改为“已撤回”并保留历史，机台恢复为“待入库” |
| 客户成品核销发货撤回 | 客户成品恢复为“未核销”，关联机台恢复为“待入库”，等待入库员确认 |

东莞仓库不再使用单独的撤回规则。东莞发货撤回与其他仓库一致，机台只恢复为“待入库”，等待入库员确认后重新入库；入库员可以选择符合业务规则的库位，不要求返回原库位。确认入库前不得增加正式库位库存。

撤回执行成功后，机台解除对原订单、配货记录和运行中流程的有效绑定与库存占用；原订单号、流程号和机台关系只保留在不可覆盖的历史记录中。待入库机台不能被配货、发货或其他业务流程占用，只允许入库确认和必要的异常处理。原订单回到“待配货”后需要重新选择机台，不能自动复用旧配货关系。

配货撤回和发货撤回的配货记录必须保留并标记为“已撤回”，不得继续参与库存占用；后续重新配货必须生成新的配货记录，不能复用或覆盖原记录。

配货记录只表达该次配货关系是否有效，不承担发货状态。成功配货后记录为“已配货”；正常发货后仍为“已配货”，发货结果由发货单及机台状态记录；配货撤回或发货撤回后，原配货记录由“已配货”转为“已撤回”。“已撤回”为该记录终态，不允许恢复为“已配货”，也不允许复用；再次配货创建新记录，并与原记录保留可追溯关系。统计有效配货及库存占用时，必须同时结合配货记录状态、发货单状态和机台当前状态，不能仅凭“已配货”判断机台仍占用在库库存。

库存大屏与机台明细采用同一统计口径：已撤回配货立即从占用数量中扣除；待入库机台不显示在库位大屏中；入库员确认入库后增加对应库位的在库数量；发货撤回成功后从已出库数量中扣除，但在入库确认前不计入在库数量。

## 5. 流程分类

流程分类按业务域维护，分类本身不决定审批权限。建议首期包括：

- 合同流程：合同创建、合同变更、合同取消、合同关联清理；
- 订单流程：创建订单、订单配货、取消订单、删除订单、订单恢复；
- 发货流程：发货确认、发货撤回、客户成品撤回发货、发货后重新配货；
- 库存流程：成品入库、撤销入库、库位转移、重新入库、库存占用释放；
- 配货流程：订单配货、撤回配货、取消预留、替换配货机台；
- 客户成品流程：客户成品登记、客户机台规划、客户成品核销发货、核销发货撤回；
- 基础资料流程：新增机型、修改机型、删除机型、删除机台档案附件；
- 数据清理流程：清理合同关联、清理订单沙盘卡片、清理排产数据。

同一流程只能有一个主分类，可以通过业务标签关联其他相关领域，避免同一个流程在多个分类中重复配置和统计。

## 6. 流程用户规则

- 流程节点配置具体用户，不按角色配置；
- 用户可以自由放置在发起、审批、执行、通知节点；
- 不限制用户所属部门或角色；
- 同一用户可以配置在多个节点；
- 允许发起人自审自批，也允许同一用户完成发起、审批和执行；
- 不做角色冲突校验；
- 已发布模型必须保存节点快照，模型修改不影响已经创建的流程实例；
- 审批节点必须配置至少一个有效用户；
- 用户被禁用或不存在时，流程进入待重新指定状态，不得自动跳过审批；
- 首期多审批用户采用任一通过，后续可扩展其他规则。

首期审批用户规则进一步明确：

- 审批人可以由管理员手动选择，也可以按后续配置的自动分配规则选择；
- 允许配置多个审批人，多人审批采用“任一通过”；
- 允许发起人自审自批；
- 允许同一用户完成发起、审批和执行；
- 审批人失效、被禁用或不存在时，由 `admin` 重新指定，不得自动跳过；
- `admin` 和 `boss` 可以强制审批或转交，但必须记录操作人、原因和原审批记录；
- 不做角色冲突校验，节点以具体用户为准。
- 任一审批人通过后，该节点的其他待审批任务自动标记为“已结束”，不得再由原审批人改变结果；所有审批人原始分配和未处理记录保留；
- 任一审批人拒绝后立即结束审批流程，不再执行逆向业务；
- `admin` 和 `boss` 可以对已结束任务进行有原因、有审计记录的管理操作，但不得直接修改历史审批记录；是否允许推翻已执行或已拒绝的整单结果，另行明确。

## 7. 统一流程路径

```text
业务操作发起
    ↓
读取已发布流程模型
    ↓
校验业务范围和当前状态
    ↓
判断处理方式
    ├─ 自动通过
    │    ↓
    │  自动执行
    │
    └─ 需要审批
         ↓
       用户审批
         ↓
       再次校验状态和版本
         ↓
       自动执行
    ↓
更新业务数据
    ↓
生成派生任务
    ↓
记录流程实例、日志和通知
```

第一阶段由实际业务提交入口管理事务，内部业务函数复用该事务的数据库连接；每张业务单据的业务变更、主实例、自动通过记录及核心执行记录同成同败。缓存刷新、通知和外部同步在对应单据事务提交后执行；重复点击、重复审批、重复执行和重复通知不得重复改变业务数据或生成派生任务。批量创建合同时按合同单据分别校验、分别提交：一张合同失败只回滚该合同及其流程记录，其他合格合同继续成功；同批次实例共享请求批次号。接口返回每张合同的成功、失败或跳过结果及原因，并分别记录失败尝试。现有入口存在整批预校验并拒绝全部合同的行为，接入该流程时须同步调整。

## 8. V8 功能板块

### 工作流程

- **流程模型**：维护流程名称、分类、方向、处理方式、业务对象、执行范围、用户节点、状态校验和版本状态；
- **流程分类**：维护所有流程的总类别及分类说明；
- **流程实例**：第一阶段记录并展示正向流程实例；逆向流程尚不生成真实实例；
- **流程任务**：第一阶段仅接入与正向流程相关的记录；逆向审批任务暂不开放。

### 审批中心

审批中心用于后续处理待审批流程、查看审批历史和执行结果。第一阶段只展示板块结构和数据占位，不开放真实逆向审批、转交、强制审批或执行按钮；正向自动通过记录可作为后续接入基础。

## 9. 数据与审计要求

每个流程实例至少记录：

- 流程实例号、流程模型编号和版本号；
- 请求批次号、幂等请求标识及同批次关联实例号；
- 业务对象类型、业务对象编号和执行范围快照；
- 执行前及目标的数据库原始状态值、展示名称和业务对象版本号；
- 发起人、审批人、执行人、通知人；
- 审批意见、执行时间、执行结果和失败原因；
- 关联的派生任务号、通知记录号和原业务操作记录。

正向业务事务回滚后，以独立事务保存失败尝试，至少记录请求关联标识、请求批次号、业务单据、流程 Key、操作人、失败阶段和原因。失败尝试在审计及批次逐单结果中可查询，不生成成功主实例，也不显示为“执行异常”实例；用户修正原因后可重新提交。重新提交保留原请求关联标识并生成可区分的尝试序号，成功提交的幂等请求不得重复执行。若独立审计写入也失败，记录结构化服务日志并告警，不得把未提交的业务或流程记录显示为成功。

流程实例创建后使用模型快照，后续修改流程模型不能改变历史实例的审批人、节点顺序和执行规则。

## 10. 事务、并发和失败处理

- 同一业务对象存在未完成流程时，禁止重复发起冲突流程；
- 审批、执行和状态复核必须使用行锁或等价版本校验；
- 整单流程任何核心对象校验失败时，整单失败，不允许静默部分成功；
- 正向业务变更和对应成功流程实例、自动通过记录在同一数据库事务内完成；任一失败则整体回滚，失败尝试另行审计留痕；
- 同一请求涉及多张单据时按单据分别创建主实例，共享请求批次号；每张单据的业务动作与对应实例必须处于同一事务边界，禁止内部业务函数自行提前提交；
- 批量创建合同时每张合同独立提交；单张失败不回滚同批次其他合同，批次返回逐单结果，不得仅返回整批成功或失败；
- 外部同步和通知采用事务后事件并支持重试；
- 无法回滚时必须标记执行异常并通知相关用户；
- 第二阶段已创建的逆向实例在审批通过后执行失败时进入“执行异常”，允许 `admin` 重新校验后重试，禁止直接强制修改业务状态；第一阶段正向业务回滚只保留失败尝试，不进入该实例状态；
- 删除类操作首期全部采用软删除；存在有效关联时禁止删除；永久删除暂不开放，恢复作为独立操作处理；
- 同一业务对象只能存在一个冲突中的未完成流程；重复发起、重复审批、重复执行和重复通知必须幂等；
- 审批和执行必须在提交前再次读取当前状态和版本，执行时使用行锁或等价版本校验。

## 11. 权限规则

- 所有人可以查看流程模型和审批信息；
- 只有 `admin` 和 `boss` 可以新建、编辑、发布、停用、删除流程模型，管理审批、转交和强制审批；
- 其他用户不能修改流程模型；
- 业务人员可以发起自己业务权限范围内的逆向操作；
- 后端必须再次校验查看、发起、审批、执行、重试和管理权限，不能只依赖前端菜单隐藏；
- 执行异常只能由 `admin` 重新校验后重试，任何人不得直接强制改业务状态。

## 12. 流程版本与发布规则

- 每次发布生成新的版本号；
- 新发起的流程使用最新已发布版本；
- 已创建的流程实例固定使用创建时的模型和节点快照；
- 停用正向必需模型的版本前，必须确认存在同一流程 Key 的其他有效已发布版本；发布、停用或回滚均需校验模型配置、触发入口、状态映射和节点有效性，避免业务入口无可用模型；
- 支持回滚到历史版本，回滚生成新的发布版本，不覆盖历史版本；
- 流程 Key 全局唯一，复制模型必须生成新的唯一 Key。

## 13. 通知规则

首期通知范围包括发起人、审批人、执行异常处理人及受影响的业务部门人员。首期采用系统消息和移动端待办；短信、邮件、企业微信等通道后续扩展。通知必须在事务提交后发送，并支持失败重试和幂等。

## 14. 分阶段范围

### 第一阶段：正向流程接入与逆向模型准备

- 正向流程接入现有业务操作，自动通过并生成流程实例、执行记录和审计日志；
- 完成六项逆向操作的流程模型、审批配置和状态快照设计；
- 完成模型、分类、版本和权限的持久化；
- 完成正向流程实例、流程任务和审批中心中的自动通过记录；
- 逆向操作只完成流程模型、版本和审批配置；
- 审批中心只展示页面结构和数据占位，不开放真实逆向审批、转交、强制审批或执行按钮；
- 第一阶段只生成正向流程的真实实例；逆向历史业务操作不补录为流程实例；
- 不修改现有逆向业务执行接口，不改变当前逆向操作结果。

第一阶段现有逆向入口属于过渡期旧操作，尚未受流程审批约束；不得将其执行结果标记为已通过流程审批。第二阶段切换时必须同时封闭全部可绕过审批的旧入口，并由后端强制所有首期逆向操作先审批再执行。

### 第二阶段：逆向审批执行

- 接入六项逆向操作的发起、审批、转交、强制审批、自动执行和异常重试；
- 完成整单事务、并发校验、库存联动和通知重试；
- 完成东莞仓库与普通仓库一致的撤回和重新入库逻辑。

### 第三阶段：流程编排扩展

- 支持自动分配审批人规则；
- 支持更复杂的条件分支、批次范围和外部系统同步；
- 评估开放部分逆向流程自动通过。

## 15. 暂不包含

- 永久物理删除；
- 短信、邮件、企业微信等外部通知通道；
- 复杂条件分支和跨系统流程编排；
- 未列入首期范围的其他逆向业务操作。
