# 预测沙盒交互研究与优化建议

## 1. 结论

当前预测沙盒的核心问题不是缺少按钮，而是把三个不同的业务决策混在一个横向卡片画布里：

1. 需求池：哪些合同需要生产、交期是什么。
2. 计划方案：合同如何分批、哪些位置作为备货、预计何时入库。
3. 执行派工：已确认批次进入哪条产线、当前是否在产。

成熟系统通常将这三层拆开，并用明确的提交闸门连接：计划可以反复计算和比较，只有确认后的版本才能进入执行。

## 2. GitHub 案例

| 项目 | 可借鉴的成熟做法 | 对本项目的启示 |
|---|---|---|
| [ERPNext](https://github.com/frappe/erpnext) | Production Plan 聚合销售订单/物料需求，支持计划数量、生产订单、物料需求和库存预留等独立步骤 | 沙盒应先生成“计划版本”，再分别处理合同需求、备货需求和物料/库存约束，不要用一张卡同时表达全部含义 |
| [Odoo](https://github.com/odoo/odoo) | Manufacturing Order、Work Order、Work Center 分层；工单有计划开始/结束、工作中心、预计时长、实际时长和状态 | 批次确认不等于开工；应把批次计划、产线派工、工序执行和实际完工拆成不同状态 |
| [frePPLe](https://github.com/frePPLe/frepple) | 将需求预测与高级计划排程分层，强调瓶颈、拉动式计划和低库存；计划结果是可解释的计划 | 沙盒应显示每个批次为何这样排、哪条约束导致延期，而不是只显示一个重算结果 |
| [Orkyo Community](https://github.com/Kymr10n/orkyo-community) | 共享可视化计划、资源能力匹配、冲突检测、利用率、请求/分配工作流；建议变更需确认后提交 | 拖拽应先产生待提交变更，显示冲突和影响，点击“应用方案”后才持久化 |
| [ProductionPlanner](https://github.com/MagdaOleksandrTeam/ProductionPlanner) | MRP-lite、贪心排程、交互式甘特图、优先级颜色和 KPI | 当前规则算法可以保留，但需要用时间轴、负荷和延期指标解释算法结果 |

## 3. 当前页面审计

| 优先级 | 已观察问题 | 影响 | 建议 |
|---|---|---|---|
| P0 | 页面同时提供“全量重算/按选中列重算”、拖拽、强改锁定、急单、特殊卡、审核、撤销审核 | 用户无法判断哪些操作只是模拟，哪些已经改变正式计划 | 引入“方案版本”概念；沙盒编辑默认只改草稿，统一通过“提交计划”进入 Confirmed |
| P0 | 预测批次和已确认批次在同一横向画布中展示 | 预测、冻结计划和执行计划的视觉边界弱，容易误操作 | 默认分成“待规划合同”“预测方案”“已确认待派工”三个视图/标签 |
| P0 | 产线派工在另一页面完成，用户需要自己记住哪些批次已确认、哪些产线空闲 | 从计划到执行存在认知断层 | 在方案详情显示“派工预览”，支持从已确认批次直接进入产线分配 |
| P1 | 空槽备货卡与合同卡都以 unit card 表示 | 备货建议可能被误认为客户承诺 | 使用独立的备货层或明确的“备货建议”标记，并显示来源和可替换性 |
| P1 | 重算结果缺少解释性摘要 | 用户只能凭卡片位置判断结果是否合理 | 增加交期达成率、延期合同数、合同台数、备货台数、产线负荷、溢出队列等指标 |
| P1 | 交期、批次容量、比例等约束隐藏在算法/配置中 | 调整结果不可预测，审核缺少依据 | 在“方案说明”中显示使用的容量、断档阈值、比例和被锁定数据 |
| P2 | 大量操作依赖右键菜单和拖拽 | 可发现性和键盘操作较弱 | 增加选中后的操作栏、撤销/重做、冲突提示；右键只保留快捷入口 |

## 4. 推荐交互模型

### 4.1 三段式工作台

```text
需求池 -> 生成方案 -> 审核提交 -> 派工执行
```

页面默认进入“需求池 + 方案摘要”，而不是直接铺满所有批次卡。

### 4.2 需求池

左侧或顶部显示合同需求列表，字段至少包括：合同号、客户、机型族、数量、要求交期、当前状态、已排/未排数量、风险。

支持按交期、机型族、客户、风险筛选。对未进入方案的合同直接显示原因：交期无效、机型未启用、容量不足、进入等待队列等。

### 4.3 方案区

方案区按批次展示，但提供两个视图：

- 批次视图：看每批合同组成、备货数量、交期范围和容量。
- 时间轴视图：看批次在日期和产线上的负荷、延期和空档。

重算后生成一个草稿版本，例如“方案 2026-09-03 14:30”。用户可以调整、比较和放弃版本。只有点击“提交方案”后才进入已确认状态。

### 4.4 统一变更预览

任何拖拽、急单插入、批次移动或比例调整都先进入变更集，顶部显示：新增延期合同、受影响批次、备货变化、产线负荷变化。

提交前必须通过：

- 机型族兼容检查；
- 批次容量检查；
- 锁定卡片保护；
- 交期风险检查；
- 已确认批次不可被草稿重算覆盖。

### 4.5 从方案到产线

提交方案后进入“待派工”列表。每个批次显示推荐产线、可用产线、不可用原因和预计开始/结束时间。即使第一阶段仍由人工选择产线，也应让系统给出推荐和校验结果。

## 5. 与现有算法的兼容方式

第一阶段不必立即替换现有算法。保留当前：

- 最早交期优先；
- G/XS/AUTO 机型族隔离；
- 固定批容量；
- 30 天交期断点；
- 比例补齐备货；
- 20 个预测槽位和等待队列。

在算法输出外增加解释数据：

```json
{
  "plan_version": "2026-09-03T14:30:00+08:00",
  "source": "factory_plan",
  "rules": {
    "capacity": {"G": 30, "XS": 30, "AUTO": 27},
    "batch_break_days": 30,
    "max_open_batches": 20
  },
  "metrics": {
    "contract_units": 0,
    "stock_units": 0,
    "late_contracts": 0,
    "queued_units": 0
  },
  "changes": []
}
```

## 6. 实施优先级

### P0：先解决误操作

1. 增加计划版本/草稿状态。
2. 把预测、已确认、待派工分开显示。
3. 统一提交前校验和变更摘要。
4. 防止全量重算覆盖已确认或已锁定数据。

### P1：提升排产判断效率

1. 增加需求池未排原因。
2. 增加交期达成率、延期数、产线负荷和队列指标。
3. 增加批次时间轴和产线派工预览。
4. 为人工产线分配提供推荐与不可用解释。

### P2：提升算法能力

1. 纳入产线能力、换型时间、班次、维护窗口。
2. 引入物料齐套和库存约束。
3. 将目标函数从单一交期/比例扩展为延期、库存、换型和产线利用率的加权优化。

## 7. 重要边界

GitHub 案例的代码质量、活跃度和产品成熟度差异很大，不能把仓库 star 数当作业务正确性的证明。ERPNext/Odoo/frePPLe 是成熟参考，Orkyo 和 ProductionPlanner 更适合借鉴交互和局部实现。第一阶段应优先改造状态和交互，不应直接引入一个新的排产引擎。
