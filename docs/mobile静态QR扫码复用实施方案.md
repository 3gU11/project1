# Mobile 静态 QR 扫码复用实施方案

## 1. 文档目的

本文档提供一套可复用于 Web、H5 和 PWA 项目的静态 QR 扫码方案。用户通过手机拍照或选择相册图片完成识别，不使用实时摄像头视频流。

方案目标：

- 优先在手机本地完成识别，降低等待时间和服务端成本。
- 本地失败后使用服务端增强识别，提高困难图片的识别成功率。
- 对多码、错码和重复绑定进行明确处理，避免静默错绑。
- 在二维码无法识别时保留重拍和人工输入通道。
- 允许根据业务要求选择是否上传和保存原始照片。

## 2. 适用范围与限制

### 2.1 适用场景

- 设备铭牌、零部件标签、资产标签和工单二维码。
- 用户拍摄单张照片后进行识别。
- 扫码结果需要人工确认后才能绑定业务对象。
- 希望在弱网或离线状态下保留基础识别能力。

### 2.2 不适用场景

- 仓库流水线连续高速扫码。
- 必须持续取景、自动追踪二维码的实时扫码。
- 二维码损坏后仍要求自动识别旁边印刷文字的场景。

本方案不包含 OCR。二维码识别最终失败时，用户只能重拍或人工输入。若项目需要识别标签印刷文字，应将 OCR 作为独立能力设计和验收，不能把 QR 解码与 OCR 混为一谈。

## 3. 总体架构

```text
拍照或选择照片
    |
    v
浏览器图片预处理
    |
    v
zxing-wasm 本地静态识别
    |-- 唯一有效结果 --> 业务格式校验 --> 用户确认
    |-- 多个不同结果 --> 标记歧义 --> 用户选择或重拍
    `-- 无结果
            |
            v
        上传原图
            |
            v
服务端 OpenCV Multi + WeChatQRCode
            |
            v
      合并、去重、业务校验
    |-- 唯一有效结果 --> 用户确认
    |-- 多个有效结果 --> 人工选择或重拍
    `-- 无结果 --------> 重拍或人工输入
```

核心原则：识别结果只是候选值，不能未经业务校验和用户确认直接绑定资产、部件或工单。

## 4. 前端实施方案

### 4.1 技术选型

- 使用 `zxing-wasm` Reader 在浏览器本地解码。
- 使用 `<input type="file" accept="image/*" capture="environment">` 或框架对应的上传组件获取照片。
- 使用 `createImageBitmap()` 和 Canvas 生成预处理候选图。
- 将 WASM 文件打包到应用静态资源，不依赖外部 CDN。

`capture="environment"` 只是浏览器提示，不能保证所有设备都直接打开后置摄像头。因此界面必须兼容相册选择。

### 4.2 图片预处理

建议依次尝试以下候选图：

1. 原图。
2. 长边限制为 1200 px 的缩放图。
3. 长边限制为 850 px 的缩放图。
4. 中心裁剪 82% 后缩放。
5. 中心裁剪 68% 后缩放。
6. 灰度化并提升对比度的中心裁剪图。

这些参数只是起始值，不是通用最优值。新项目必须根据二维码尺寸、拍摄距离、标签材质和手机型号重新测试。

### 4.3 解码参数示例

```ts
const results = await readBarcodes(image, {
  formats: ['QRCode'],
  tryHarder: true,
  tryRotate: true,
  tryInvert: true,
  tryDownscale: true,
  tryDenoise: true,
  maxNumberOfSymbols: 8,
})
```

### 4.4 前端处理规则

- 对相同结果去重。
- 发现多个不同二维码时，不得自动选择第一个。
- 设置识别中状态，阻止重复提交。
- 处理图片损坏、浏览器不支持、内存不足和解码超时。
- 释放 `ImageBitmap`、Canvas 和临时对象，避免连续拍照后内存累积。
- 本地识别成功后，根据业务要求决定是否仍需上传照片归档。
- 离线时允许继续本地识别；服务端回退应显示为暂不可用，而不是阻塞人工输入。

## 5. 服务端实施方案

### 5.1 技术选型

- `opencv-contrib-python-headless`
- `cv2.QRCodeDetector`
- `cv2.wechat_qrcode_WeChatQRCode`
- WeChatQRCode 官方检测和超分辨率模型

不要在同一 Python 环境混装相同版本的 `opencv-python` 和 `opencv-contrib-python-headless`。两者都提供 `cv2`，混装可能造成模块覆盖和部署结果不一致。

### 5.2 解码策略

高风险业务建议同时执行两个解码器并合并结果：

```python
multi_values = decode_with_opencv_multi(image)
wechat_values = decode_with_wechat_qrcode(image)
values = deduplicate(multi_values + wechat_values)
```

两种解码器具有互补性，不建议直接用 WeChatQRCode 替换 OpenCV Multi。

若更重视平均响应速度而不是完整性，可以先运行 WeChatQRCode，失败后再运行 Multi。但这种提前返回策略可能无法发现两个解码器给出不同结果的歧义，不适合资产绑定、序列号或生产追溯等高风险业务。

### 5.3 服务端安全限制

- 只接受 JPEG、PNG、WebP 等白名单格式。
- 限制上传文件大小、图片尺寸和解码后的总像素数。
- 不允许客户端提交任意服务器文件路径。
- 设置请求超时、并发限制和速率限制。
- 使用 HTTPS 传输包含生产标签的照片。
- 明确照片保存期限、访问权限和删除机制。
- 服务启动时检查 WeChatQRCode 能力和模型文件完整性。

## 6. API 契约

### 6.1 图片识别接口

```http
POST /api/qr/decode
Content-Type: multipart/form-data
```

建议响应：

```json
{
  "success": true,
  "status": "unique",
  "values": ["1111"],
  "value": "1111",
  "sources": ["zxing_wasm", "opencv_multi"],
  "ambiguous": false,
  "duration_ms": 126
}
```

状态定义：

| 状态 | 含义 |
| --- | --- |
| `unique` | 只有一个通过业务校验的结果 |
| `ambiguous` | 存在多个不同的有效结果 |
| `not_found` | 没有识别到二维码 |
| `invalid_format` | 已解码，但内容不符合业务格式 |
| `error` | 图片损坏、服务异常或识别超时 |

### 6.2 业务确认接口

识别和业务绑定必须使用两个不同接口。例如：

```http
POST /api/assets/{assetId}/qr-confirmation
```

建议保存：

- `raw_value`
- `confirmed_value`
- `recognition_sources`
- `confirmed_by`
- `confirmed_at`
- `photo_id`
- `manual_corrected`
- `decoder_versions`

## 7. 业务校验与防错

二维码解码成功后仍需执行：

- 长度、字符集、前缀和校验位检查。
- 是否属于当前任务允许的物料或资产范围。
- 是否已经绑定其他对象。
- 是否与当前操作位置、工位或部件类型一致。
- 是否需要二次确认或复核权限。

物理位置编号应来自当前任务配置，二维码只提供标签自身编码。不能让扫码结果覆盖任务位置，否则扫错标签可能形成格式合法但业务错误的组合编号。

## 8. 数据与状态设计

建议状态：

```text
pending
  -> processing
  -> recognized
  -> ambiguous
  -> not_found
  -> confirmed
  -> manually_entered
  -> rejected
```

至少记录以下审计信息：

- 原始识别值和最终确认值。
- 使用的解码器及版本。
- 是否经过人工修改。
- 操作人、确认人和时间。
- 对应照片或照片摘要。
- 失败原因和重拍次数。

## 9. 分阶段实施

| 优先级 | 实施内容 | 发布条件 |
| --- | --- | --- |
| P0 | 拍照/选图、`zxing-wasm`、人工确认、人工输入 | 基础业务流程可完成 |
| P1 | OpenCV Multi + WeChatQRCode 服务端回退 | 困难样本识别率达到项目目标 |
| P1 | 格式校验、重复绑定检查、审计记录 | 不产生静默错绑 |
| P2 | PWA 离线缓存、识别指标和失败样本分析 | 支持持续监控和优化 |
| P2 | 根据真实样本调优裁剪与增强参数 | 量化证明有收益后发布 |

## 10. 测试与验收

### 10.1 样本要求

上线前至少收集 100 至 300 张真实照片，覆盖：

- 正常光线、低光、过曝和反光。
- 倾斜、旋转和透视变形。
- 远距离小二维码。
- 对焦模糊、运动模糊和低质量 JPEG。
- 污损、折痕和缺角。
- 单码、多码和非目标二维码。
- 项目实际使用的主流手机与浏览器。

### 10.2 建议验收指标

- 唯一正确识别率不低于项目约定值；一般项目可从 95% 作为初始目标。
- 错误自动绑定率必须为 0。
- 多码场景不得静默选择。
- 前端本地识别 P95 不超过 1 秒。
- 完整服务端回退 P95 不超过 2 秒。
- 服务端不可用时，本地识别和人工输入仍可使用。
- 每次确认均能追溯来源、原值、修改人和解码器版本。

### 10.3 已验证经验的适用边界

V8 历史测试中，OpenCV 官方数据集包含 56 张图片、85 个预期二维码：

| 方案 | 正确识别 | 样本结果 |
| --- | ---: | ---: |
| WeChatQRCode + 官方模型 | 61/85 | 71.8% |
| OpenCV Multi | 76/85 | 89.4% |
| 两者结果合并 | 79/85 | 92.9% |

该结果只证明两个解码器在该测试集上具有互补性，不能直接作为其他项目的预期识别率。不同二维码尺寸、打印质量、标签材质、拍摄距离和设备分布都会改变结果。

## 11. 部署检查清单

- [ ] `zxing-wasm` 与 WASM 文件已随前端产物发布。
- [ ] 离线或弱网环境下本地解码可运行。
- [ ] 服务端仅安装一种 OpenCV Python wheel。
- [ ] WeChatQRCode 四个模型存在且校验通过。
- [ ] 上传大小、像素数、超时和并发限制已配置。
- [ ] HTTPS、鉴权和照片访问控制已启用。
- [ ] 多码、无结果、错误格式和人工输入路径已验证。
- [ ] 不会在未经确认的情况下自动绑定业务对象。
- [ ] 识别耗时、成功率、歧义率和人工修正率可观测。
- [ ] 已使用项目真实照片完成回归测试。

## 12. 推荐默认方案

对于普通企业移动端项目，建议默认采用：

```text
zxing-wasm 本地静态识别
-> OpenCV Multi 与 WeChatQRCode 服务端互补识别
-> 结果合并、去重和业务格式校验
-> 用户确认
-> 重拍或人工输入兜底
```

准确率优化应以真实失败样本为依据。不要仅凭开源项目热度、单张成功图片或实验室数据替换解码器，也不要通过自动选择第一个结果来掩盖多码歧义。
