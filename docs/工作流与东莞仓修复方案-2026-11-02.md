## 二、P0-1 失败实例锁死业务对象

### 2.1 实测证据

| 触发动作 | 用户看到 | 后续后果 |
|---|---|---|
| `allocation-recall` 明细传成 `订单` 而不是 `机台` | `409 撤回配货流程缺少有效机台明细` | `order-delete` → `409 业务对象已有未完成逆向流程: WF-...` |
| `stock-transfer` 目标库位已满 | `422 库位 C05 已满载` | 该机台 `customer-finished-recall` → `409 业务对象已有未完成逆向流程` |
| `customer-finished-recall` 前置状态不满足 | `409 客户成品当前不可撤回` | 同上 |
| `shipment-confirm` 未选机台 | `422 请先勾选至少 1 台机台` | 实例残留（`business_id=BATCH-xxx`） |

系统给出的三条恢复通道全部无效：

```
POST /workflows/instances/{no}/withdraw   → 409 流程当前状态为执行异常，不能执行该操作
POST /workflows/instances/close-stale     → count: 0（要求 created_at < NOW()-1h）
重复提交同一业务对象                       → 409 业务对象已有未完成逆向流程
```

本次测试最终**手工改库**处理了 7 个实例才能继续（见附录 A）。

### 2.2 根因

1. **先建实例、后执行**：`create_reverse_instance` 先落 `workflow_instances`，执行器随后抛错时由 `mark_execution_failure`（`crud/workflows.py:1677`）把状态置为 `执行异常`。
2. **执行异常被当作"未完成"**：冲突校验 `crud/workflows.py:1085-1091` 的未完成状态集合包含 `执行异常`，因此同一业务对象的所有后续逆向流程都被拒绝。
3. **撤回只允许审批中**：`transition_reverse_instance`（`crud/workflows.py:1220-1230`）里 `withdraw` 的 `before` 状态写死为 `审批中`。
4. **陈旧清理有 1 小时门槛**：`close_stale_reverse_instances`（`crud/workflows.py:1716`）虽然覆盖 `执行异常`，但 `hours = max(1, max_age_hours)`，刚产生的实例永远进不了清理范围。
5. **明细在创建时冻结**：执行器从 `workflow_instance_items` 读明细（如 `execute_allocation_recall` `crud/workflows.py:1387`），重试时无法替换，一旦传错就必然卡死。

### 2.3 修复方案（分三层，可分批上线）

#### 修复 A —— 止血：开放"立即作废"通道（约 0.5 天）

1. `transition_reverse_instance` 新增 `abandon` 动作：

```python
allowed = {
    'approve': ('审批中', '已通过', '通过'),
    'reject':  ('审批中', '已拒绝', '拒绝'),
    'withdraw': ('审批中', '已撤回', '撤回'),
    # 新增：执行失败/卡住的实例允许管理角色作废，释放业务对象
    'abandon': ('执行异常', '已作废', '作废'),
}
```

要求：仅 `admin`/`boss`、必须填 `reason`、写 `workflow_audit_logs`、释放 `workflow_object_locks`、关闭未完成 `workflow_tasks`、`workflow_instance_items.execution_result='已作废'`。

2. 新增路由 `POST /api/v1/workflows/instances/{instance_no}/abandon`（与 withdraw 同构，权限更严）。

3. `CloseStaleRequest.max_age_hours` 下限由 1 放宽到 0：

```python
hours = max(0, int(max_age_hours or 24))   # 原来 max(1, ...)
```

4. 前端「流程实例」页对 `执行异常` 行增加「作废并释放」按钮（二次确认 + 必填原因）。

#### 修复 B —— 减少产生：前置校验前移（约 1 天）

在 `submit_reverse_instance` 建实例之前，按 `workflow_key` 执行可预判的校验，把"注定失败"的提交挡在门外：

| workflow_key | 前置校验 | 复用逻辑 |
|---|---|---|
| `allocation-recall` | items 必须全部为 `机台`，且非空 | 现 `crud/workflows.py:1407` 的检查前移 |
| `stock-transfer` | 目标库位容量足够（`get_slot_capacity` + 当前占用数） | `crud/inventory.py` |
| `customer-finished-recall` | 机台状态 ∈ {已发货, 已出库, 库存中（DG-WH）} | 现 `crud/workflows.py:1647` 前移 |
| `shipment-recall` | 机台可撤回（`_shipment_recall_eligible`） | 已有函数 |

实现建议：`crud/workflows.py` 增加 `PRECONDITION_CHECKS = {key: callable}`，在 `submit_reverse_instance` 的 `try` 之前调用；失败直接 `409`，不建实例。

#### 修复 C —— 根治：失败可重试（约 2-3 天，可与 B 合并）

1. `mark_execution_failure` 区分错误类型：
   - 业务校验类（`ValueError` / `BatchPlanningError` 等）→ 状态置 `可重试`，保留租约释放，允许重新提交明细
   - 系统类（DB/网络）→ 保持 `执行异常`
2. 新增 `POST /workflows/instances/{no}/retry`：允许携带新的 `items`，覆盖 `workflow_instance_items` 后重新执行（需校验业务对象未被其他实例占用）。
3. 或者放宽冲突校验：同一业务对象存在 `执行异常` 实例时，允许发起新流程并**自动作废旧实例**（写审计），避免用户被历史垃圾卡住。

> 建议先上 A（止血），再上 B（降发生），C 视排期。

## 三、P1-1 东莞单机订单无法"确认出货"

### 3.0 业务确认结论：**设计如此，已关闭**（2026-11-02）

业务方确认口径：

> **东莞客户的「已发货」就是发到东莞仓库中。**

因此：

| 现象 | 结论 |
|---|---|
| 发货确认后订单立即 `done`、机台停在 `库存中（DG-WH）` | ✅ 正确。`DG-WH` 是客户仓，进去即视为已交付 |
| 单机东莞订单发完后「确认出货」按钮不可用 | ✅ 正确。该按钮的含义是"把该订单还在**待发货**的机台发出去"，此时已无待发货机台 |
| `mark_shipped` 执行后机台仍是 `库存中（DG-WH）` 而非 `已出库` | ✅ 正确。这正是"发到东莞仓"的落地状态，不存在第二次出库核销 |
| `customer-finished-recall` 接受 `库存中（DG-WH）` | ✅ 正确。撤销发货就是把东莞仓的机台退回待入库 |

**结论：P1-1、P1-2 均关闭，不实施任何代码改动。**
原 3.1/3.2、4.1/4.2 的改法仅作为"若将来业务改口要求客户仓再出库"时的备选，不再推进。

> 遗留的真实问题不在语义，而在**代码判定口径不统一**（4 套写法）与**12 台历史数据错位**，
> 见 `docs/WORKFLOW_DG_RISK_ANALYSIS.md` 5.1 / 5.2，以及本文 3.3。

### 3.1 根因

- `_customer_order_action_preview`（`api/routes/inventory.py:599`）对 `action=mark_shipped` 的判定：

```python
if status in {"done","deleted","canceled","cancelled","pending_review"} \
        or progress.get(oid, {}).get("order_status_label") == "已完成":
    reason = "已完成、已取消、已删除或待二次确认的订单不能执行此操作"
```

- 而 `confirm_shipping` 统计"已发"时把客户仓机台算进去（`api/routes/inventory.py:1744`）：

```sql
WHERE (`状态`='已出库' OR (`状态` LIKE '库存中%' AND `Location_Code`='DG-WH'))
```

单机订单一旦发货进 DG-WH，`need=1 / shipped=1` → 订单立即 `done` → 预览恒为不可执行。

### 3.2 方案（备选，**不推进**）

> 业务已确认"东莞已发货 = 发到东莞仓"，本节保留为将来业务改口时的备选。

**方案 A（改动小、风险低）**：把 `done` 的拒绝条件收窄

```python
shipped = [...]  # 先算出该订单在客户仓/已出库的机台
blocked_by_status = status in {"deleted","canceled","cancelled","pending_review"}
if payload.action == "mark_shipped" and blocked_by_status:
    reason = "..."
elif payload.action == "mark_shipped" and status == "done" and not shipped:
    reason = "已完成、已取消、已删除或待二次确认的订单不能执行此操作"
```

即：**订单已完成但仍有客户仓机台待核销时，允许确认出货**。

**方案 B（语义更正确，改动大）**：DG-WH 机台不计入订单完成度
- 修改 `inventory.py:1744` 的 shipped 口径，排除 `库存中（DG-WH）`；
- 订单保持 `ready`，待客户核销后再置 `done`；
- 需同步核对：报表出货数、看板完成数、`order_progress` 的 `待发货` 判定、沙盘释放逻辑。

> 若采用 B，则 P1-2 的语义问题也一并解决；建议先做 A 止血，B 单独立项评估口径影响。

### 3.3 验证用例

1. 单机东莞单：配货 → 发货（进 DG-WH）→ **确认出货**（应 `can_execute=true`）→ 核销撤回 → 重入库。
2. 非东莞单机订单：发货 → 确认出货仍应被拒绝（不能误放行）。
3. 已删除/已取消订单：确认出货仍被拒绝。

### 3.4 遗留：判定口径与历史数据（与 P1-1/P1-2 无关，需单独决策）

业务口径明确后，代码里"东莞仓"仍存在 4 种写法，历史库里也有 12 台机台对不上：

```
状态 = '库存中（DG-WH）'，但 Location_Code 是 C04/C05/C07/F08/F09/F10/新厂一楼小机床存放区
→ 共 12 台，全部属于订单 SO-20260918-53E2，订单至今 status=active
```

后果：按库位判定的地方（订单完成计数、退换货候选、取消订单完整性）认为"未发货"，
按状态判定的地方（订单删除、发货撤回、条件节点）认为"已发货"，订单既完不成也删不掉。

两条路，需业务/仓储确认后二选一：

| 方案 | 做法 | 风险 |
|---|---|---|
| 修数据 | 把这 12 台的 `Location_Code` 改成 `DG-WH`（状态已是 DG-WH） | 若机台实际仍在原库位，库位大屏会失真，需仓储确认实物位置 |
| 修代码 | 统一到"状态优先"的单一判定函数（如 `is_shipped_machine`），库位只作辅助 | 改动面涉及 12 处调用，需要回归报表/看板/退换货 |

推荐：先由仓储确认这 12 台的实物位置，再决定；确认在东莞仓则修数据，确认不在则修代码口径。

## 四、P1-2 客户仓"确认出货"不改变机台状态

> **状态：已关闭（设计如此）** —— 东莞的"已发货"就是发到东莞仓，`库存中（DG-WH）`
> 即终态，不存在第二次出库核销。以下内容仅作存档。

### 4.1 根因

`execute_customer_order_shipped`（`crud/workflows.py:1602`）直接复用 `confirm_shipping`：

```python
return {**confirm_shipping(ShippingActionPayload(serial_nos=[...], expected_order_no=...),
        None, worker_id, {'username': worker_id}, workflow_execution={...}),
        'instance_no': instance_no, 'status': '已完成'}
```

而 `confirm_shipping` 对东莞客户走客户仓分支（`api/routes/inventory.py:1705`），机台被置为 `库存中（DG-WH）`，**不会变成"已出库"**。

但 `execute_customer_finished_recall`（`crud/workflows.py:1647`）又把 `库存中（DG-WH）` 视为"已核销"，两处对"客户已出货"的定义不一致。

### 4.2 方案（备选，**不推进**）

为"客户核销出货"提供独立执行路径，不再复用发货确认：

1. 在 `execute_customer_order_shipped` 内新增分支（或新建 `execute_customer_ack_shipment`）：
   - 机台状态 `库存中（DG-WH）` → `已出库`
   - `Location_Code` 清空（或保留 `DG-WH` 作为历史字段，需产品确认）
   - 写 `shipping_history`（`flow_type='客户仓出库'`）+ 审计 + `workflow_audit_logs`
   - 触发订单完成判定（与 `confirm_shipping` 同一口径）
2. 同步统一 `customer-finished-recall` 的前置条件：只认 `已出库`（客户仓出库后的状态），不再接受 `库存中（DG-WH）`；或按"是否走过核销"标记区分。
3. 若采用 P1-1 方案 B，则本项可简化为"核销后置 `已出库` + 订单置 `done`"。

### 4.3 验证用例

1. 东莞单：配货 → 发货（DG-WH）→ 确认出货 → 机台应为 `已出库`（不再是 `库存中（DG-WH）`）。
2. 核销撤回 → 机台回 `库存中（DG-WH）` 或 `待入库`（按业务确认），派生重入库任务可关闭。
3. 客户成品列表/报表在两种状态下数量正确。
