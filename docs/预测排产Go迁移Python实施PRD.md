# 预测排产 Go 渐进迁移 Python 实施 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品/系统 | V8BetaV1.1 预测沙盘与生产看板排产服务 |
| 文档类型 | 后端渐进迁移实施 PRD |
| 版本 | V1.0 |
| 日期 | 2026-09-03 |
| 目标技术栈 | Python 3 + FastAPI + Pydantic + SQLAlchemy/MySQL |
| 迁移方式 | 保持外部接口兼容的分阶段替换，不一次性推倒重写 |
| 关联文档 | 《预测沙盒前端交互重构PRD》 |

## 2. 执行摘要

本项目将预测沙盘与生产看板相关的 Go 排产能力逐步迁入现有 FastAPI 服务，前端继续访问 `/api/v1/sandbox/*`，迁移期间不要求前端同步改接口。

本项目的目的不是单纯减少一种语言，而是解决以下工程问题：

1. FastAPI 与 Go 之间存在代理、鉴权、错误转换和领域规则重复。
2. FastAPI 已直接实现部分沙盘写操作，服务边界不完整，跨实现事务可能出现半成功。
3. Go 服务异常会使依赖代理的沙盘接口返回 502。
4. Go 自动化测试覆盖薄弱，算法迁移缺少可证明的行为基线。
5. 启动脚本可能复用旧 Go 可执行文件，源码与运行版本存在不一致风险。

迁移成功的判断不是“Python 接口能返回数据”，而是同时满足：

- HTTP 与 WebSocket 契约兼容；
- 相同数据快照产生相同或经业务批准的等价排产结果；
- 并发、事务、锁和幂等行为不退化；
- 性能满足基于现网 Go 基线定义的发布门槛；
- 任一阶段均可切回 Go；
- Go 仍承载的 Mobile 拍照能力有明确保留或迁移决定。

## 3. 前提校正与决策

### 3.1 已核实事实

| 事实 | 当前证据 | 影响 |
|---|---|---|
| 前端统一请求 FastAPI 沙盘路径 | `frontend/src/services/sandboxApi.ts` | 可在网关层切换实现，前端无需感知迁移 |
| FastAPI 将大量请求代理到 Go 3001 | `api/routes/sandbox.py` 的 `GO_SANDBOX_URL` 与 `_forward` | 当前请求链路多一跳，Go 不可用时代理接口不可用 |
| FastAPI 已直接实现调货、同步计划等沙盘操作 | `api/routes/sandbox.py` | 排产业务边界已经横跨 Python 与 Go |
| Go 承载批次、重算、比例和产线路由 | `server/internal/router/router.go` | 核心迁移不能只搬运预测算法 |
| Go 预测核心使用数据库事务和锁 | `server/internal/engine/predictor.go`、仓储层与 `server/internal/lock/lock.go` | Python 版本必须复现并发保护，不可只翻译计算代码 |
| Redis 不可用时 Go 锁会退化到单进程本地锁 | `server/internal/lock/lock.go` | 多进程部署下不能继续依赖仅进程内互斥 |
| FastAPI 将重算视为长请求 | `api/routes/sandbox.py` | Python 重算不能阻塞异步事件循环 |
| Go 同时承载 Mobile 拍照相关接口 | `server/internal/router/router.go` | 排产迁移完成不等于可以关闭 Go 进程 |

### 3.2 错误前提与逻辑跳跃

| 前提 | 判断 | 正确处理 |
|---|---|---|
| “统一成 Python 就能保证通信协议一致” | 不成立 | 用 OpenAPI、Pydantic 模型、统一枚举、错误码与契约测试保证一致性 |
| “重写后性能一定下降” | 未经压测不能下结论 | 先建立 Go 基线，再以同数据、同硬件、同并发对比 |
| “排产迁移后可以直接删除 Go” | 当前不成立 | 先盘点并处置 Mobile 拍照接口和其他调用方 |
| “逐行翻译即可得到相同算法” | 风险很高 | 先冻结黄金数据集和业务不变量，再重建领域实现并双跑 |
| “Python 服务内加一个普通锁即可” | 多进程下不成立 | 使用数据库命名锁、锁表或可靠的分布式锁，并保留行锁 |

### 3.3 已选方案

采用“绞杀式渐进迁移”：FastAPI 保持唯一外部入口，按能力逐项将路由从 Go 代理切换为 Python 原生实现。每个能力均经过契约测试、影子双跑、灰度切流和回滚验证后再进入下一阶段。

不采用以下方案：

- 一次性重写并整包切换；
- 同一写请求同时写 Go 和 Python 两套数据；
- 在没有黄金数据集和性能基线时按主观判断宣布等价；
- 为迁移顺便重做前端流程或改变排产业务规则。

## 4. 目标与非目标

### 4.1 P0 目标

1. 前端接口地址、主要请求字段、响应字段和 WebSocket 事件保持兼容。
2. FIFO、比例补齐、批次容量、交期断点、锁定保护、急单和线内调度等结果与现有有效规则一致。
3. 批次确认及同步待排产改为单一事务操作，不留下“已确认但未同步”或“已同步但未确认”的中间状态。
4. 同一时刻同一排产域只允许一个有效重算任务，重复提交可识别并幂等处理。
5. 已确认、生产中和已完成数据不会被普通重算覆盖。
6. 每个迁移能力都可以通过配置在不重新发布前端的情况下切回 Go。
7. 迁移过程不在预测沙盘重复建设合同管理的待规划功能，也不重复建设生产看板的待派工和产线执行页面。

### 4.2 P1 目标

1. 统一排产领域模型、状态枚举、权限与错误码。
2. 增加排产任务 ID、方案版本和结构化审计日志。
3. 重算改为后台任务或进程池执行，避免占用 FastAPI 事件循环。
4. 建立算法差异报告与可重复性能基准。
5. 降低对 Go 服务运行状态和旧可执行文件的依赖。

### 4.3 P2 目标

1. 在排产迁移稳定后评估 Mobile 拍照模块是否迁移到 Python。
2. 根据压测结果决定是否拆出独立 Python 排产 worker。
3. 清理确认无调用的 Go 排产代码、代理代码和启动项。

### 4.4 非目标

- 不将预测沙盘升级为 APS。
- 不引入新的全局最优排程算法。
- 不在本项目中改变 BOSS 设置比例、合同按交期/FIFO 进入队列的产品规则。
- 不在本项目中重构合同管理和生产看板前端。
- 不承诺 Python 天然比 Go 更快或更慢。
- 不改变 MySQL 为其他数据库。
- 不在未审批的情况下重算或修复历史生产数据。

## 6. 当前架构与主要缺口

### 6.1 当前调用链

```text
PC 前端
  -> FastAPI 8000 /api/v1/sandbox/*
       -> Python 直接实现的部分接口 -> MySQL
       -> HTTP 代理 -> Go 3001 /api/* -> MySQL
       -> WebSocket 代理 -> Go 3001 /ws

Mobile 前端
  -> FastAPI 8000（通用 API）
  -> Go 3001（部分拍照/机台任务 API）
```

### 6.2 当前缺口

| 编号 | 缺口 | 后果 | 优先级 |
|---|---|---|---|
| G-01 | 同一领域由 Python 与 Go 共同写库 | 事务边界分裂，排障困难 | P0 |
| G-02 | 错误、权限和机型分类存在重复实现 | 两边规则可能漂移 | P0 |
| G-03 | 确认批次和同步计划为两个动作 | 网络或服务异常时可能半成功 | P0 |
| G-04 | 缺少系统化算法回归集 | 无法证明重写结果一致 | P0 |
| G-05 | 重算是长耗时调用 | Python 实现不当会阻塞其他 API | P0 |
| G-06 | 本地锁无法覆盖多进程实例 | 并发重算可能互相覆盖 | P0 |
| G-07 | WebSocket 经 Python 转发 Go | 断线、事件丢失和错误定位链路长 | P1 |
| G-08 | Go 仍有非排产调用方 | 提前下线会造成 Mobile 回归 | P0 |

## 8. 领域规则迁移基线

### 8.1 排序和合同进入

1. 合同按要求交期升序进入对应大类队列。
2. 同交期按“进入排产池时间”FIFO；正式实施前必须确认该字段及历史数据策略。
3. 普通合同不得自动插入已确认或生产中批次。
4. 交期提前或延后先形成调度建议，涉及冻结区时走受控调整。
5. 无法归类、缺交期或容量不足的数据必须返回明确原因，不允许静默丢弃。

### 8.2 机型分类和比例

1. 对 BOSS 展示时，XS 族的中小型与中大型合并为一个 100% 比例池；AUTO 族同理。
2. 内部仍必须保留中小型和中大型分类，因为批次容量、产线兼容或其他执行规则可能不同。
3. 比例仅影响未确认预测区，通过合同队列后移和备货建议补齐目标比例。
4. 真实合同不得因比例不足或超出而删除。
5. 取整默认采用最大余数法，保证总槽位数不变；若当前 Go 结果不同，以业务确认后的规则为准。
6. 每次重算保存比例快照、分类版本、容量配置和算法版本。

### 8.3 批次与容量

迁移前必须从当前配置和 Go 代码冻结容量矩阵。现阶段需至少覆盖 30、27、16 三种容量场景，但不得把这些值散落为 Python 魔法数字。

容量、交期断点、最大开放批次数等参数统一进入版本化配置，并由领域服务读取。配置变更需要操作者、时间和变更前后值。

### 8.4 状态保护

| 状态 | 普通重算 | 人工移动 | 确认/撤销 | 派工/调度 |
|---|---:|---:|---:|---:|
| Predicted | 可处理 | 可处理 | 可确认 | 不可直接派工 |
| Confirmed | 不可覆盖 | 先撤销确认 | 可在未派工时撤销 | 可派工 |
| In_Production | 不可覆盖 | 仅受控调度 | 不可撤销确认 | 可线内调度 |
| Completed | 不可覆盖 | 不可修改 | 不可操作 | 不可修改历史 |

### 8.5 锁定、急单和调货

- 锁定卡片在重算后必须保留业务位置；无法保留时整次重算失败或进入明确冲突，不得静默移动。
- 急单插入必须明确被级联后移的合同和批次，并保持容量不变量。
- 调货/交换涉及的所有单元必须在同一数据库事务内锁定、校验和提交。
- 三方置换任一环节失败时整体回滚。

## 9. API 契约要求

### 9.1 路径兼容原则

- 外部基路径继续使用 `/api/v1/sandbox`。
- 迁移期间前端不直接访问 Go 3001。
- 单个能力通过后端 feature flag 决定调用 Python 或 Go。
- 路径、HTTP 方法、必填字段、默认值、状态码和响应结构均纳入契约测试。
- 允许增加可选字段，不允许无版本地删除字段或改变字段类型。

### 9.2 统一响应和错误

建议成功响应继续兼容现有结构，同时所有新实现至少提供请求追踪 ID。错误响应统一为：

```json
{
  "detail": "该批次已进入生产，不能撤销确认",
  "code": "BATCH_ALREADY_IN_PRODUCTION",
  "request_id": "req_20260903_xxx",
  "retryable": false,
  "context": {
    "batch_id": "BATCH-001"
  }
}
```

P0 错误码至少覆盖：

- 权限不足；
- 数据版本冲突；
- 重算任务已运行；
- 批次容量冲突；
- 状态不允许；
- 卡片已锁定；
- 机型/产线不兼容；
- 合同或批次不存在；
- 数据库锁等待超时；
- 依赖服务不可用。

### 9.3 幂等要求

以下写接口必须支持 `Idempotency-Key` 或业务等价幂等键：

- 全量/局部重算提交；
- 批量确认；
- 确认并同步计划；
- 急单插入；
- 产线派工；
- 手工完工；
- 调货与线内调度。

重复请求不得重复创建批次、重复同步计划或重复移动生产单元。

### 9.4 OpenAPI 管理

1. 阶段 0 从现有实际请求/响应生成契约快照。
2. 前端 TypeScript 类型优先从 OpenAPI 生成或由 CI 校验。
3. Go 旧实现和 Python 新实现对相同契约用例运行。
4. 契约变化必须有版本记录和兼容性评审。

## 10. 数据与事务一致性

### 10.1 事务边界

| 用例 | 必须处于同一事务的操作 |
|---|---|
| 重算 | 锁定排产域、读取快照、替换未确认批次、写单元位置、写任务结果与审计 |
| 确认并同步 | 校验批次、更新确认状态、写入待排产/计划数据、写审计与 outbox |
| 撤销确认 | 校验未派工、删除/撤销同步记录、恢复状态、写审计 |
| 急单插入 | 锁定相关批次与单元、插入、级联后移、容量校验、提交 |
| 调货/交换 | 锁定所有参与单元与位置、校验、置换、写审计 |
| 派工 | 锁定批次和产线、校验空闲/兼容性、绑定产线、更新状态、写事件 |
| 完工 | 锁定产线任务、更新完成状态、释放产线、写后续事件 |

### 10.2 并发控制

1. 数据库读改写沿用 `SELECT ... FOR UPDATE` 或 SQLAlchemy 等价写法。
2. 重算使用跨进程有效的全局锁，不接受仅 `asyncio.Lock`、线程锁或进程内变量。
3. 批次和方案增加版本号，写入时执行乐观锁检查。
4. 锁获取需设置超时，失败返回可识别业务错误，不无限等待。
5. 所有数据库连接、事务和锁在异常路径中必须释放。

### 10.3 数据迁移

本项目优先原表兼容，避免同时迁代码与迁核心数据结构。确需新增时，只允许增加：

- `scheduling_job`：重算任务、状态、进度、算法版本、输入摘要、结果摘要；
- `scheduling_audit_log`：领域操作前后值和原因；
- `scheduling_idempotency`：幂等键与结果；
- `scheduling_outbox`：事务内事件；
- 方案版本或锁版本字段。

所有 DDL 必须满足向后兼容：Go 旧实现可以继续读取核心表；新增列有安全默认值；回滚代码时无需回滚数据。

### 10.4 数据校验不变量

每次写操作提交前后至少校验：

- 同一生产单元不能同时出现在两个有效位置；
- 批次有效单元数不得超过容量；
- 已确认/生产中/已完成记录不会被预测重算删除；
- 单元状态与所在区域一致；
- 产线同一时刻只绑定允许数量的活动批次；
- 确认状态与计划同步记录一致；
- 事务失败时上述字段无部分变化。

## 11. WebSocket 与领域事件

### 11.1 兼容要求

- 外部地址继续使用 `/api/v1/sandbox/ws`。
- 现有事件名称、字段和触发时机先冻结为契约。
- Python 迁移后由统一 WebSocket manager 发送事件，不再转发 Go `/ws`。
- 客户端断线重连后必须主动刷新权威数据，不把 WebSocket 当作唯一数据源。

### 11.2 可靠事件

影响数据库状态的事件使用 transactional outbox：业务事务和待发送事件同事务落库，后台发送成功后标记完成。至少包含：

- `forecast.recompute.started/completed/failed`；
- `batch.confirmed/revoked`；
- `batch.synced_to_plan`；
- `unit.moved/swapped/rush_inserted`；
- `production_line.assigned/completed/reordered`。

事件至少带 `event_id`、`occurred_at`、`actor_id`、`aggregate_id`、`version` 和 `request_id`，客户端按 `event_id` 去重。

## 12. 重算执行模型

### 12.1 推荐实现

1. HTTP 请求创建重算任务，快速返回 `job_id`。
2. worker 或受控进程池执行 CPU 密集计算。
3. 任务状态通过查询接口和 WebSocket 更新。
4. 算法先基于一致性快照计算候选结果。
5. 提交前重新检查数据版本；版本变化则标记冲突，不覆盖新数据。
6. 在短事务内锁定并写入最终结果。

兼容期内可保留同步等待模式，但内部不得直接在 FastAPI 事件循环执行 CPU 密集计算。

### 12.2 任务状态

```text
Pending -> Running -> Validating -> Committing -> Succeeded
                    -> Conflicted
                    -> Failed
                    -> Cancelled（仅提交前允许）
```

### 12.3 重复与取消

- 同一大类已有运行任务时，重复请求返回已有任务 ID 或明确冲突。
- 已进入 `Committing` 的任务不可取消。
- 客户端超时或关闭页面不取消后台任务。
- worker 异常退出后，超时任务可被标记失败并安全重试。

## 13. 算法等价定义

### 13.1 必须完全一致的结果

- 合同集合与数量；
- 未排/等待集合及原因；
- 批次容量约束；
- 状态保护结果；
- 锁定对象位置或冲突结果；
- 急单和人工调度的最终位置；
- 确认、派工和完工状态转换。

### 13.2 允许业务等价的结果

当旧算法在完全相同优先级下依赖数据库返回顺序时，Python 可以产生不同但合法的顺序，但必须先定义稳定的最终 tie-breaker。建议依次使用：

1. 要求交期；
2. 进入排产池时间；
3. 合同号；
4. 生产单元 ID。

任何“等价但不逐项相同”都必须有差异分类和业务负责人签字，不得由开发人员自行忽略。

### 13.3 黄金数据集

阶段 0 建立去敏、可重复导入的黄金数据集，至少包括：

- 空数据、单合同、满批和跨批；
- 同交期 FIFO；
- 30 天边界前后；
- 30、27、16 容量；
- XS/AUTO 合并比例池但内部尺寸不同；
- 最大余数取整；
- 已锁定、已确认、生产中和已完成；
- 急单级联后移；
- 调货三方置换；
- 交期提前与延后；
- 非法机型、缺失交期、容量溢出；
- 并发重算和并发人工移动。

黄金输入、Go 输出、Python 输出、规则版本和差异审批必须纳入版本管理；不得包含真实客户敏感数据。

## 14. 性能与容量要求

### 14.1 说明

以下数字是建议的发布门槛，不是当前已经测得的性能事实。阶段 0 必须先在固定硬件、固定数据库快照下测量 Go 基线，再由技术负责人确认最终阈值。

### 14.2 建议发布门槛

| 场景 | 建议门槛 |
|---|---|
| 普通读写接口 | Python P95 不超过 Go 基线的 1.2 倍，错误率不增加 |
| 全量重算 | Python P95 不超过 Go 基线的 1.3 倍 |
| FastAPI 可用性 | 重算期间非重算接口仍可响应，事件循环无明显阻塞 |
| 数据库影响 | 锁等待、死锁和连接池耗尽不高于 Go 基线 |
| 内存 | 峰值在部署资源预算内，无随任务次数持续增长 |
| WebSocket | 事件不重复写业务状态；断线恢复后数据最终一致 |

### 14.3 压测矩阵

必须覆盖：

- 小、中、大三种数据规模，规模由生产脱敏样本的 P50、P90、最大合理值定义；
- 1、5、20 个并发用户；
- 只读、普通写入、全量重算、重算与查询混合负载；
- 单 FastAPI 进程与生产计划部署进程数；
- 冷启动、热缓存和数据库慢查询场景。

记录吞吐、P50/P95/P99、CPU、内存、数据库连接数、锁等待、死锁和任务排队时间。

## 15. 权限、安全与审计

1. 沿用 FastAPI 统一登录身份和权限判断，不信任前端传入角色。
2. Python 原生接口与现有代理接口的权限结果必须一致。
3. 所有关键写操作记录操作者、角色、业务原因、请求 ID、幂等键及前后值摘要。
4. 日志不记录密码、令牌、完整客户敏感信息或完整请求体。
5. 重算、确认、撤销、派工、完工和跨线调度属于高价值审计动作。
6. 管理员的 feature flag 切换必须留审计记录。

## 16. 可观测性

### 16.1 指标

- 每个路由按实现来源标记 `implementation=go|python`；
- 请求量、成功率、P95/P99 和错误码；
- 重算排队、计算、校验和提交耗时；
- Go/Python 双跑一致率和差异类型；
- 数据库事务耗时、回滚数、锁等待和死锁；
- WebSocket 连接数、发送失败、重连和 outbox 积压；
- feature flag 当前值与切换记录。

### 16.2 日志关联

一次业务操作使用同一 `request_id`/`job_id` 关联：前端请求、FastAPI、可选 Go 影子调用、数据库事务、审计记录和 WebSocket 事件。

### 16.3 告警

P0 告警条件至少包括：

- 重算连续失败；
- 算法结果出现合同丢失、重复或状态保护失败；
- 数据库死锁/锁等待显著增加；
- 确认状态与计划同步数据不一致；
- Python 灰度错误率超过 Go 基线阈值；
- outbox 持续积压；
- 回滚开关不可用。

## 17. 分阶段实施计划

### 阶段 0：冻结契约和基线（P0）

交付物：

- HTTP/OpenAPI 与 WebSocket 契约快照；
- 状态枚举、权限矩阵和错误码表；
- 黄金数据集和 Go 基准输出；
- Go 性能基线报告；
- feature flag、路由选择和回滚骨架；
- 数据表与调用方清单，特别标明 Mobile 依赖。

完成门槛：代表性现有接口契约测试可重复运行；黄金场景能够从固定数据库快照生成一致 Go 输出。

### 阶段 1：迁移只读接口（P0）

范围：

- 批次列表和详情；
- 产线列表；
- 比例查询；
- 待排产/生产队列查询；
- 机型分类和只读配置。

策略：Python 与 Go 同时读取同一快照，在后台对响应做规范化比较；用户仍接收主实现结果。

完成门槛：契约 100% 通过；核心字段一致；灰度期间错误率和响应时间满足门槛。

### 阶段 2：迁移简单写接口（P0）

范围：

- 比例保存；
- 批次确认与撤销确认；
- 批量确认；
- “确认并同步待排产”原子用例。

关键改造：将当前分开的确认与同步收敛为一个应用服务和一个数据库事务；旧接口可保留为兼容壳。

完成门槛：注入网络异常、数据库异常和重复请求后，无半成功、重复同步或状态错乱。

### 阶段 3：迁移复杂调度写操作（P0/P1）

范围：

- 单元前移、后移和跨批移动；
- 槽位重排与内容交换；
- 急单插入、转急单和返回沙盘；
- 调货和三方置换；
- 派工、锁定、完工和线内调度。

关键改造：统一状态校验、行锁顺序、幂等和审计；通过固定锁顺序降低死锁概率。

完成门槛：事务/并发测试通过，任一失败点均整体回滚，生产状态保护测试 100% 通过。

### 阶段 4：迁移预测重算算法（P0）

范围：

- 全量重算；
- 按大类重算；
- 比例归一化与备货补齐；
- 批次容量、交期断点、锁定保护与等待队列。

策略：

1. Python 先只做影子计算，不写数据库。
2. 对同一快照运行 Go 与 Python。
3. 规范化后比较批次、单元顺序、数量、比例、备货和等待队列。
4. 差异自动分类；阻断级差异不得灰度。
5. 通过后以少量指定用户/大类灰度 Python 写入。

完成门槛：全部黄金场景通过；连续业务样本达到评审确定的一致率，且不存在合同丢失、重复、越容量或冻结数据变化。

### 阶段 5：迁移 WebSocket 与全面切流（P1）

范围：

- Python 原生沙盘 WebSocket；
- transactional outbox；
- 前端断线重连与权威数据刷新；
- 排产路由默认切换到 Python。

完成门槛：事件契约通过；故障恢复测试通过；Go 排产代理流量降至 0 并稳定运行一个观察周期。

### 阶段 6：Go 退出决策（P2）

1. 再次扫描 Go 调用方、路由和端口流量。
2. 对 Mobile 拍照模块选择：保留独立 Go 小服务、迁移 Python，或由其他服务承接。
3. 只有所有调用方清零、回滚观察期结束、归档与运行手册完成后，才能移除 Go 排产代码和启动项。

排产切流完成但 Mobile 仍调用 Go 时，只能缩减 Go 职责，不能停止 Go 进程。

## 18. 双跑、灰度与切流

### 18.1 Feature flag

建议按能力配置，不使用一个全局布尔值：

```text
sandbox.read_batches = go | python | shadow
sandbox.batch_write = go | python
sandbox.dispatch_write = go | python
sandbox.recompute = go | python | shadow
sandbox.websocket = go | python
```

支持按用户、角色、机型大类或指定环境灰度；切换操作必须审计。

### 18.2 双跑原则

- 只读和纯计算可自动双跑。
- 写操作禁止两边同时提交数据库。
- 写操作双跑时，副实现只能基于隔离快照模拟并比较，不产生持久化副作用。
- 对时间戳、随机 ID、数据库自增 ID 等非业务字段先规范化再比较。
- 差异报告必须能定位到合同、单元、批次、规则和算法版本。

### 18.3 灰度顺序

开发环境 -> 固定黄金数据 -> 内部管理员 -> 指定 BOSS/排产员 -> 指定机型大类 -> 全量用户。

每一档至少观察一个完整排产业务周期，具体时长由实际排产频率决定，不固定拍脑袋设置天数。

## 19. 回滚方案

### 19.1 回滚触发条件

出现以下任一情况立即停止扩大灰度，并评估切回 Go：

- 合同丢失、重复、跨状态覆盖或容量越界；
- 确认与待排产同步不一致；
- 生产线队列错误或完工状态错误；
- 算法出现未批准的业务差异；
- 错误率、超时或锁等待超过发布门槛；
- Python 服务不可用且自动降级失败。

### 19.2 回滚步骤

1. 禁止新的 Python 重算和高风险写操作。
2. 等待已进入 `Committing` 的事务完成，不强行中断数据库提交。
3. 核对最后成功的 `request_id`、任务状态和数据不变量。
4. 将对应能力 flag 切回 Go。
5. 清理或标记未提交的 Python 任务，不删除审计与 outbox 证据。
6. 对异常时间窗执行数据一致性校验。
7. 恢复流量后复测批次查询、确认、派工和代表性重算。

### 19.3 数据回滚原则

- 优先代码/流量回滚，不回滚兼容性 DDL。
- 不通过整库恢复处理单次业务错误，除非完成影响范围确认并获得批准。
- 已提交的生产调度通过受控反向操作修复，不直接改历史记录。
- 回滚演练必须在正式灰度前完成并计时。

## 21. P0 业务验收场景

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 同交期合同进入 | 按权威进入时间 FIFO，结果稳定可重复 |
| AC-02 | 比例总和与取整 | 比例池总计 100%，总槽位不因取整增减 |
| AC-03 | XS 比例 | 中小型与中大型共同参与 XS 族比例，内部尺寸信息仍保留 |
| AC-04 | AUTO 比例 | 中小型与中大型共同参与 AUTO 族比例，内部尺寸信息仍保留 |

| AC-06 | 比例重排 | 合同仅后移或进入后续队列，真实合同不被删除，备货补齐可解释 |
| AC-07 | 锁定卡片 | 重算保留锁定对象；无法保留时明确冲突并不提交 |
| AC-08 | 冻结数据保护 | Confirmed、In_Production、Completed 不被普通重算修改 |
| AC-09 | 急单插入 | 被影响队列按规则级联后移，容量与合同数量守恒 |
| AC-10 | 调货三方置换 | 三方全部成功或全部回滚，无中间状态 |
| AC-11 | 确认并同步 | 一个业务操作原子完成，重复提交不重复写计划 |
| AC-12 | 撤销确认 | 已派工批次被阻止；未派工批次状态与同步记录同时恢复 |
| AC-13 | 派工与完工 | 状态和产线绑定一致，不兼容产线被阻止 |
| AC-14 | 线内调度 | 顺序、锁定和被影响合同正确，操作有审计 |
| AC-15 | 并发重算 | 同一排产域仅一个任务提交，其他请求返回已有任务或冲突 |
| AC-16 | 并发写入 | 行锁和版本冲突生效，不发生丢失更新 |
| AC-17 | 服务异常 | 事务回滚，用户得到稳定错误码，可安全重试 |
| AC-18 | WebSocket | 事件名称和载荷兼容，断线重连后刷新得到权威状态 |
| AC-19 | Go 回滚 | 单项 flag 切回后前端无需变更即可继续使用 |
| AC-20 | Mobile 回归 | 排产迁移不破坏仍由 Go 提供的拍照与机台任务接口 |

## 24. 风险与应对

| 风险 | 概率/影响 | 应对 |
|---|---|---|
| 旧算法存在隐含数据库顺序 | 高/高 | 增加稳定 tie-breaker，差异必须业务评审 |
| Python CPU 计算阻塞 API | 中/高 | worker 或进程池，任务化重算，压测混合流量 |
| Python 多进程锁失效 | 中/高 | 数据库或可靠分布式锁，配合行锁和版本号 |
| 双写造成数据污染 | 中/高 | 写操作永不双提交，影子实现只读隔离快照 |
| 原表被两种实现写入 | 高/高 | 按能力单写者原则，feature flag 明确所有权 |
| 迁移顺便修改业务规则 | 中/高 | 算法等价与规则优化拆分发布、分别审批 |
| Mobile 依赖被遗漏 | 中/高 | 阶段 0 调用方清单，阶段 6 独立退出门槛 |
| 性能目标脱离实际 | 中/中 | 先测 Go 基线，再批准相对/绝对阈值 |
| 工作区或发布包复用旧 Go EXE | 中/中 | 构建产物带 commit/version，启动健康信息展示版本 |
| 单体 FastAPI 故障域扩大 | 中/高 | worker 隔离、连接池配额、限流、健康检查和后续拆服务选项 |

## 25. 待确认事项

以下问题会改变实现，必须在对应阶段开始前确认：

1. FIFO 权威时间是合同创建、审核通过还是进入排产池时间。建议使用进入排产池时间。
2. 当前生产环境实际启用的容量矩阵、30 天断点和最大开放批次数，以数据库配置还是 Go 默认值为准。
3. 比例取整是否正式采用最大余数法；若与 Go 历史结果不同，是否作为单独规则变更发布。
4. `确认批次` 与 `同步待排产` 是否允许产品层面合并为一个动作。建议合并，旧接口仅兼容。
5. 重算采用独立任务进程、进程池还是现有任务基础设施；需结合部署方式和压测决定。
6. 跨进程重算锁选用数据库命名锁、专用锁表还是 Redis；不能仅依据开发环境决定。
7. 灰度观察周期按每天/每周实际排产频率如何定义。
8. Mobile 拍照 Go 模块长期保留为小服务，还是进入下一期 Python 迁移。
9. Go 与 Python 出现“业务等价但顺序不同”时，由谁批准差异。
10. 生产数据脱敏样本的提取、保存期限和访问权限。

## 26. 推荐启动顺序

在上述待确认事项尚未全部解决前，可以立即启动且不会造成返工的工作只有：

1. 生成并冻结现有 HTTP/WebSocket 契约。
2. 建立状态、权限、错误码和机型分类清单。
3. 构建黄金数据提取与结果规范化工具。
4. 测量 Go 基线，不预设 Python 性能结论。
5. 增加按能力切换的 feature flag 和观测标签。

阶段 0 通过评审后，再开始迁移任何写接口或重算算法。
