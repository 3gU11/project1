# 经销商订单转合同：按批次/来源自动选路与机台单行备注

整理日期：2026-10-28。依据当前工作区代码，未做线上联调。

## 1. 背景

经销商订单（`dealer_orders`）的每条明细都带「批次/来源」：

- `batch_no`：`FINISHED-STOCK` / `库存中` 表示现货，具体值（如 `09-10`、`10-02`）表示生产批次；
- `inventory_type`：`finished`（成品现货）、`wip`（在产批次）、`heightened`（加高批次）、`unmarked`（未标记）。

改造前，转合同弹窗让操作员手动选择「进入沙盘 / 进入生产看板 / 使用现货」，选择结果只影响合同状态，**与明细的批次/来源无关**；批次/来源只被写进合同的「指定批次/来源」，用于急单自动插单优先批次和合同管理页展示。

现在改为：**按每行明细的批次/来源自动判定路径**。库存中行合同直接置「已规划」，具体批次行置「待规划」进入沙盘。**机台分配仍由业务人员在「订单配货」手动完成**；每行备注按「单行备注」口径写到机台合同备注，供人工判别和后续追溯。

## 2. 路径判定规则

判定与 `crud/dealer_orders.py::_is_finished_stock_order` 同口径，前后端各实现一份，必须保持一致：

| 明细行条件 | 判定 | 路径 |
| --- | --- | --- |
| `inventory_type` ∈ `finished / stock / 现货` | 库存中 | 现货：合同「已规划」 |
| `batch_no` 为空（含未下发批次） | 库存中 | 现货：合同「已规划」 |
| `batch_no` ∈ `FINISHED-STOCK / 库存中 / 现货 / 现货库存` | 库存中 | 现货：合同「已规划」 |
| 其余（如 `09-10`） | 具体批次 | 沙盘：合同「待规划」 |

同一张经销商订单可以混合两种来源，例如库中真实数据就存在「库存中 + 10-02 批次」同一订单的情况。

## 3. 转合同流程

```mermaid
flowchart TD
    A[经销商订单审核通过] --> B[打开转合同弹窗\n明细行显示自动路径]
    B --> C[提交转合同]
    C --> D{按明细批次/来源分组}
    D -->|库存中行| E[现货组: 合同状态=已规划]
    D -->|具体批次行| F[批次组: 合同状态=待规划]
    E --> G[新建现货合同\n逐行写单行备注]
    F --> H[新建批次合同\n写指定批次/来源]
    G --> I[回写经销商订单\n逐行写各自合同号]
    H --> I
    I --> J[业务人员人工处理]
    J --> K[现货: 销售订单→导入已规划合同→订单配货\n按需求行单行备注手动勾选机台]
    J --> L[批次: 沙盘/按批次规划并配货]
```

要点：

1. **同路径合并**：同一路径的多条明细只生成**一张**合同；同机型同加高规格的明细行合并为一行并累加数量，加高与普通规格不合并。
2. **混合订单拆两张合同**：现货组一张、批次组一张。前端预取的合同号给首行所在路径，另一张按合同号尾部 4 位序号顺延（如 `HT202610280001` → `HT202610280002`），并校验不重复。
3. **不自动建单、不自动配货**：库存中合同停在「已规划」，由业务人员到「销售订单 → 导入已规划合同」建单，再到「订单配货」手动判别分配机台。
4. **批次组仍走沙盘**：合同「待规划」，`指定批次/来源` 保留 `{批次号: 数量}`，急单开关与急单卡逻辑不变。

## 4. 机台单行备注

实现：`utils/order_notes.py::single_line_order_remark`。

### 4.1 取值规则

合同行备注可能是多段拼接：

```
[总]整单备注 加高 [备注]原备注 [附加]附加备注 [改数]2
```

机台只保留**一行**可打印备注，优先级：

1. `[备注]` 原备注
2. `[附加]` 附加备注
3. 「加高」独立标记 / `[改数]` 改数量（两者都有时写成 `加高 改数2`）
4. 以上都没有时，把分段标记剥掉后的原文压成一行；`[总]` 整单备注不属于单行备注

换行、制表符和连续空格统一压成单个空格。历史/外部无分段备注原样保留。

### 4.2 展示与落库

- **订单配货页**：需求分解表新增「单行备注」列，按「机型 + 加高规格」汇总展示该行明细的单行备注；机台列表的「合同备注」列也按单行口径展示。
- **人工配货确认后**：`crud/orders.py::_build_model_note_map` 从订单关联的合同行取单行备注，`allocate_inventory` 把它写到机台的 `finished_goods_data.合同备注`（在产机台写 `units.order_remark`）。
- **落库保留分段前缀**：写到机台时，原备注存为 `[备注]原文`、附加备注存为 `[附加]原文`（`utils/order_notes.py::machine_remark_text`）。这样备注正文里的「加高」说明文字（例如「400G加高100mm 配单滤水箱」）不会被后续 `hasHighHint` 当成加高信号，避免普通机台被误判成加高；加高/改数本身是语义标记，按纯文本落库。库存查询、发货复核、仓库看板、机台修改、订单配货等展示列都用 `singleLineOrderRemark` 去掉前缀后显示。
- 订单明细接口（`GET /planning/orders/{order_id}/details`）每行同时返回原始 `备注` 与 `单行备注`，前端默认展示后者；加高判断仍用原始分段备注，避免说明文字里的「加高」误判。

## 5. 失败与回滚

转合同同一请求内只创建合同：

1. 第二张合同创建失败时，删除本次已建合同、合同通知和未处理的急单卡；
2. 回写经销商订单失败时同样删除已建合同；
3. 回滚是补偿式而非跨模块原子事务（合同落库使用独立的整表重写逻辑），极端情况下失败点之后的外部副作用（如 Go 沙盘急单卡/重算）无法撤销。

因为不再自动配货，不存在机台占用回滚问题。

## 6. 接口变更

`POST /api/v1/dealer-orders/{order_no}/convert-to-contract`

请求：

- `items` 每行新增 `batch_no`、`inventory_type`（前端从经销商订单行带入）；缺省时后端回退到订单行。

响应新增：

```json
{
  "contract_no": "HT202610280001、HT202610280002",
  "contract_ids": ["HT202610280001", "HT202610280002"],
  "contracts": [
    {"contract_no": "HT202610280001", "path": "spot", "path_label": "库存中 → 现货直配（合同已规划）",
     "row_count": 2, "qty": 3, "models": ["FR-400G", "FH-300C"]},
    {"contract_no": "HT202610280002", "path": "batch", "path_label": "批次 → 沙盘待规划",
     "row_count": 1, "qty": 2, "models": ["FR-400G"]}
  ],
  "save_mode": "auto"
}
```

`save_mode` 请求字段已废弃（保留仅为兼容旧客户端，后端不再据此选路）；响应 `save_mode` 固定为 `auto`。原有 `rush_created`、`rush_auto_inserted`、`cloud_attachments`、`order_form_attached_contracts` 保留。

`GET /api/v1/planning/orders/{order_id}/details` 的 `details` 每行新增 `单行备注`。

## 8. 边界与未改变的行为

- 具体批次行不会自动按批次预占机台，仍由沙盘/合同管理的「按批次规划并配货」处理；指定批次作为优先项写入合同。
- 库存中行不把 `FINISHED-STOCK/库存中` 写进合同「指定批次/来源」。
- 转合同仍要求经销商订单全部明细为「已通过」，附件归档、云端附件回传、订货单挂附件逻辑不变。
- 单行备注只影响机台展示和人工判别，不改变配货的机型/加高匹配规则。
