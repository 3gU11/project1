# 维修系统每日快照上传脚本开发说明

## 1. 目的

在 V8 本地系统中增加一个面向维修系统的出站快照上传模块。V8 完成机台拍照、OCR 识别、人工确认和机台/零件绑定后，每天自动生成一次维修系统需要的基础资料快照，并主动上传到维修云端。

本模块参考当前 V8 `cloud_sync_outbox` 和 `V8_connection` 的出站方式，但不直接复用现有的 V7 API Key，也不上传可执行 SQL。上传内容是经过字段白名单、规范化和摘要计算的结构化行数据；云端接收服务负责校验后，在维修系统数据库中暂存和原子发布。

## 2. 不可改变的边界

1. V8 的 `rjfinshed` 数据库只允许 V8 本地程序读取，维修云端不能反向访问。
2. V8 本地程序只向云端发起出站 HTTPS 请求，不需要给工厂路由器配置入站端口。
3. V8 使用专用只读数据库账号读取同步所需表，禁止使用数据库 `root`。
4. 不上传 `INSERT`、`DELETE`、`UPDATE` 等可执行 SQL，不提供任意 SQL 接口。
5. 上传的数据只包含维修业务需要的字段，不把整行 V8 记录原样转发。
6. 每个自然日最多生成一个业务快照；网络失败时可以重试同一个快照，但不能生成多个不同快照覆盖云端。
7. 云端接收后先暂存和校验，校验失败或数量异常时继续使用上一版活动数据。

## 3. 组件和数据流

```text
V8 工厂内网

rjfinshed MySQL
    |
    | 只读查询；照片、OCR、绑定事务已经提交
    v
repair_sync.snapshot_builder
    |
    | 规范化字段、校验、生成快照摘要
    v
repair_sync_snapshots（本地不可变快照）
    |
    | cloud_sync_outbox：每天一个 event_id
    v
repair_sync.client（HTTPS + mTLS + HMAC）
    |
    | 出站 443，重试使用相同 snapshotId 和幂等键
    v
公网 Nginx/WAF（sync.repair.example.com）
    |
    | mTLS、请求大小限制、限流、仅代理同步路径
    v
repair-v8-connection（云端，仅监听 127.0.0.1）
    |
    | 验签 -> Schema 校验 -> 暂存 -> 业务校验 -> 原子发布
    v
维修系统 MySQL
    |
    v
维修 API 的活动快照 -> 客户端物料选择、绑定核验、保修判断
```

云端接收服务不连接 V8 本地数据库，也不保存 V8 数据库密码。Nginx 只暴露专用同步域名和同步路径，其他路径全部返回 `404`。

## 4. 与 V8 现有代码的衔接

### 4.1 可复用部分

现有文件已经提供了可复用的基础能力：

- `crud/cloud_sync_outbox.py`：事件表、失败重试、幂等 `event_id`、后台 worker。
- `crud/cloud_dealer_order_sync.py`：共享 `httpx.Client`、`trust_env=False`、云端 URL 配置读取方式。
- `api/main.py`：FastAPI 启动和关闭 worker 的位置。
- `wechat_sync/`：本地同步模块、安装脚本和运维说明的组织方式。

### 4.2 不应直接复用的部分

现有 `V7_API_KEY`、`X-V7-API-KEY` 和 `V8_SYNC_SECRET` 不用于维修基础资料同步。维修同步必须拥有独立的：

- `clientId`。
- `keyId`。
- HMAC 密钥。
- mTLS 客户端证书和私钥。

现有订单同步的固定 API Key 可以继续服务原有业务，但不要让它获得维修快照接口权限。维修同步也不应使用浏览器登录 Cookie 或 CORS。

## 5. 每日任务规则

### 5.1 默认时间

默认使用北京时间每天 `02:30` 生成和上传一次：

```text
REPAIR_SYNC_TIME=02:30
REPAIR_SYNC_TIMEZONE=Asia/Shanghai
```

时间必须可配置，不要写死在代码里。任务生成的是“当前完整状态快照”，不是只取过去 24 小时的增量，因此即使某天没有新机台，也能验证 V8 和云端数据是否一致。

### 5.2 快照前置条件

生成快照前必须确认：

1. V8 的拍照、OCR 和人工绑定事务已经提交。
2. 必要表存在，必要字段存在，数据库连接可用。
3. 当前有效绑定全部满足允许的审核状态。
4. 机型、配置项、机台绑定之间没有孤立引用或重复键。
5. 查询使用同一个一致性读事务，不能分别查询到不同时间点的数据。

默认允许的绑定审核状态：

```text
REPAIR_SYNC_ALLOWED_CHECK_STATUS=manual_passed,passed,approved
```

如果存在 `active=1` 但仍处于待识别、待人工确认或失败状态的绑定，默认整次快照进入 `rejected`，不把这条记录静默删除后上传。这样可以避免云端把一个尚未完成的 V8 数据状态当成完整事实。

### 5.3 每日去重和漏跑补偿

本地建立唯一业务键：

```text
repair_snapshot:YYYY-MM-DD
```

例如 `repair_snapshot:2026-07-16`。生成快照前通过数据库唯一索引和 MySQL advisory lock 防止多进程重复生成：

```sql
SELECT GET_LOCK('v8_repair_daily_snapshot', 0);
```

任务完成后必须释放锁。V8 使用多个 Uvicorn worker 时，只有拿到锁的进程执行生成；其他进程直接退出本次调度。

应用当天未运行、机器关机或定时任务错过时，V8 启动或 Windows 计划任务再次执行 `daily` 命令，发现当日没有成功快照后自动补跑。重试时沿用同一 `snapshotId` 和 `Idempotency-Key`，不创建新的业务日期版本。

## 7. 本地快照表

不要只把大段 JSON 放进 `cloud_sync_outbox.payload_json`。应增加一个不可变快照表，outbox 只保存快照 ID；这样重试时发送的内容不会因为 V8 当前数据库变化而改变。

建议表名：`repair_sync_snapshots`。

```sql
CREATE TABLE IF NOT EXISTS repair_sync_snapshots (
  snapshot_id VARCHAR(64) NOT NULL PRIMARY KEY,
  business_date DATE NOT NULL,
  schema_version VARCHAR(32) NOT NULL,
  dataset_type VARCHAR(64) NOT NULL,
  payload_json LONGTEXT NOT NULL,
  payload_sha256 CHAR(64) NOT NULL,
  record_count INT NOT NULL DEFAULT 0,
  machine_count INT NOT NULL DEFAULT 0,
  source_watermark_json JSON NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'created',
  last_error TEXT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  uploaded_at DATETIME NULL,
  UNIQUE KEY uq_repair_snapshot_date (business_date, dataset_type),
  KEY idx_repair_snapshot_status (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

生产环境如果单个快照超过数据库 `LONGTEXT` 或 Nginx 请求上限，应改为本地加密文件加分片上传；第一版在生成前限制未压缩 JSON 不超过 8 MB，压缩后请求不超过 10 MB。

## 8. 维修系统目标数据结构

上传的是下面这些表的“行数据”，不是 SQL 语句。云端接收服务把行数据写入自己的 staging 表，再映射到维修系统正式表。

### 8.1 `machines`

```text
machine_no      <- machine_no
model           <- model_name
customer        <- 云端默认空字符串；不从 V8 上传客户地址
agent           <- 云端默认空字符串；不从 V8 上传联系人
factory_date    <- 默认 NULL，除非以后明确增加白名单字段
warranty_start <- delivery_date
warranty_end   <- 由维修系统按保修规则计算，不由 V8 上传
status          <- machine_status
```

`machine_no` 是主键。一个机台在快照中只能出现一次。

### 8.2 `materials`

```text
material_code           <- material_code
name                    <- material_name
type                    <- material_type
spec                    <- material_spec
track_serial            <- 1
default_warranty_months <- 12（维修系统默认值，可配置）
source                  <- 'V8_SYNC'
```

相同 `material_code` 的字段必须一致，否则整次快照拒绝。

### 8.3 `material_instances`

```text
serial_no   <- component_serial_no
material_code <- material_code
batch_no    <- instance_batch_no
flow_no     <- instance_flow_no
produced_at <- bound_at（没有生产日期时保持 NULL）
status      <- active=1 时为 '在机'，否则为 '已解绑'
source      <- 'V8_SYNC'
```

`component_serial_no` 为空的绑定不能上传。一个零件编号不能同时对应两个有效物料编码。

### 8.4 `machine_material_bindings`

```text
id          <- 稳定生成：V8-{binding_key}，长度必须 <= 40
machine_no  <- machine_no
serial_no   <- component_serial_no
position    <- position_name（保留 position_code 在扩展字段中）
bound_at    <- bound_at
unbound_at  <- NULL；历史解绑由 active=0 表示
active      <- active
source      <- 'V8_SYNC'
work_order_no <- ''
```

有效唯一键为 `(machine_no, position_code)`。云端 staging 表必须单独保存 `position_code`，不能只依赖展示名称。

### 8.5 机型和维修物料配置

维修客户端目前读取 V8 机型拍照配置快照。为保持后续云端部署可行，建议一并上传以下结构化表：

```text
model_dictionary:
  model_code/model_name, model_family, sort_order, enabled

photo_item_library:
  position_code, item_name, sort_order, enabled

model_photo_config:
  model_code/model_name, position_code, required, enabled, sort_order
```

第一版只传客户端选择和服务器校验需要的字段，不传 `shooting_requirement`、OCR 原文、图片文件名、识别置信度和审核人员。客户端卡片只展示 `item_name`。

V8 的自增 `id` 不直接作为维修系统主键。机型使用稳定的 `model_name` 或单独的 `model_code`；配置项使用 `position_code`。这样两个系统的自增 ID 不一致时不会发生错误绑定。

## 9. 快照请求格式

推荐一个快照包同时包含四类行数据，避免机型和绑定关系分开发布造成短暂不一致：

```json
{
  "schemaVersion": "repair-v8-snapshot-1",
  "snapshotId": "018f0000-0000-7000-8000-000000000001",
  "businessDate": "2026-07-16",
  "generatedAt": "2026-07-16T02:30:12+08:00",
  "source": {
    "system": "V8",
    "database": "rjfinshed",
    "queryVersion": "repair-base-v1"
  },
  "counts": {
    "machines": 2,
    "materials": 14,
    "materialInstances": 14,
    "bindings": 17,
    "models": 28,
    "photoItems": 17,
    "modelPhotoConfigs": 392
  },
  "recordsSha256": "规范化 records 的 SHA-256",
  "tables": {
    "machines": [],
    "materials": [],
    "materialInstances": [],
    "machineMaterialBindings": [],
    "modelDictionary": [],
    "photoItemLibrary": [],
    "modelPhotoConfig": []
  }
}
```

要求：

- JSON 使用 UTF-8，无 BOM。
- 所有数组按稳定主键排序后再计算摘要。
- 空字符串、`NULL`、日期和布尔值的表示方式固定在契约中。
- `counts` 必须和实际数组长度一致。
- 未声明字段一律拒绝，不能“接收后忽略”。
- 请求体只允许 JSON；不允许携带 SQL、脚本、文件路径或数据库连接参数。

## 10. V8 读取和生成流程

### 10.1 一致性读取

生成器必须使用一个只读事务读取所有来源表：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;

-- 读取 machine_component_bindings
-- 读取 model_dictionary
-- 读取 photo_item_library
-- 读取 model_photo_config

COMMIT;
```

实际 SQL 使用参数绑定，禁止用字符串拼接表名、条件值或用户输入。读取完成后记录各表 `MAX(updated_at)` 作为 `sourceWatermark`。

### 10.2 绑定行过滤

默认选择：

```sql
WHERE active = 1
  AND TRIM(machine_no) <> ''
  AND TRIM(component_serial_no) <> ''
  AND TRIM(position_code) <> ''
  AND check_status IN ('manual_passed', 'passed', 'approved')
```

如果业务需要把失效绑定传给维修系统进行历史追踪，可以另设 `includeInactive=true` 的契约字段，但不能把失效行误当作有效行。第一版以有效绑定和当前维修查询为主。

### 10.3 生成前校验

生成器在写入本地快照前必须检查：

- `binding_key` 不重复。
- `(machine_no, position_code)` 不重复。
- `component_serial_no` 不为空且不对应多个有效物料。
- `material_code`、`material_name`、`position_code` 有值。
- `model_name` 能在机型字典中找到。
- 每个 `model_photo_config.position_code` 能在物料配置项中找到。
- 客户、代理商、地址、文件名、OCR 原文等字段没有进入输出对象。
- 数据数量没有异常归零；异常时生成失败报告，不生成可上传快照。

如果 V8 中存在未完成的有效绑定，必须在日志中列出数量和脱敏定位键，并将快照标记为 `rejected`，不能为了让任务“成功”而自动删掉这些行。

## 11. Outbox 事件设计

在 `crud/cloud_sync_outbox.py` 中新增事件类型：

```python
SYNC_EVENT_TYPES = {
    # 现有事件...
    "repair_snapshot_sync",
}
```

事件建议：

```text
event_id: v8-repair-snapshot-20260716
event_type: repair_snapshot_sync
biz_key: repair_snapshot:2026-07-16
payload_json: {"snapshot_id":"...","payload_sha256":"..."}
```

`event_id` 必须由业务日期生成，不使用每次重试都变化的随机 UUID。重复 enqueue 使用 `ON DUPLICATE KEY UPDATE` 保留同一个成功事件，不重新覆盖已经 `synced` 的记录。

处理事件时：

1. 根据 `snapshot_id` 从 `repair_sync_snapshots` 读取不可变 payload。
2. 校验本地 payload 摘要与 outbox 摘要一致。
3. 使用同一个 `snapshotId`、`event_id` 和幂等键上传。
4. 只有收到明确的 2xx 成功响应才标记 outbox 为 `synced`。
5. 网络错误、超时、429、5xx 使用同一幂等键重试。
6. 401、403、422 等配置或数据错误停止无限重试并告警。

现有 outbox worker 如果以多个 Uvicorn worker 启动，需要补充行级租约或数据库锁，避免两个进程同时处理同一事件。更稳妥的方式是让每日生成和发送命令由单独的 Windows 计划任务运行，V8 API worker 只提供查询状态接口。

## 12. 上传认证和签名

### 12.1 请求头

```http
POST /api/integrations/v8/snapshots
Host: sync.repair.example.com
Content-Type: application/json
Content-Encoding: gzip
X-V8-Client-Id: v8-factory-01
X-V8-Key-Id: 2026-01
X-V8-Timestamp: 1784140212
X-V8-Nonce: 5f3b...uuid
X-V8-Content-SHA256: 64位小写十六进制
Idempotency-Key: v8-repair-snapshot-20260716
X-V8-Signature: Base64(HMAC-SHA256)
```

### 12.2 规范化签名串

```text
HTTP_METHOD\n
REQUEST_PATH\n
CLIENT_ID\n
KEY_ID\n
TIMESTAMP\n
NONCE\n
IDEMPOTENCY_KEY\n
CONTENT_SHA256
```

签名使用独立的 32 字节以上随机密钥。云端必须：

- 校验时间戳和服务器时间差不超过 5 分钟。
- 对 `clientId + nonce` 做一次性消费，防止重放。
- 使用常量时间比较 HMAC。
- 重新计算请求体 SHA-256，不能只信请求头。
- 检查幂等键已存在时，摘要必须和第一次请求相同。
- 对验签失败和异常频率执行限流、记录和告警。

HTTPS 保证传输机密性，HMAC 保证请求确实来自登记的 V8 代理并且内容未被修改；正式环境两者都要启用，不能只依赖其中一项。

### 12.3 密钥保存

本地：

- HMAC 密钥保存在 Windows Credential Manager，或只允许运行账号读取的配置文件中。
- mTLS 私钥放在 ACL 受限目录，禁止放进 Git、项目压缩包、截图和日志。
- `.env` 只保留变量名示例，不提交真实值。

云端：

- HMAC 密钥放在云密钥管理服务或只允许运维账号读取的 Secret 文件中。
- 接收服务的数据库用户与主维修 API 用户分离。
- 密钥轮换使用 `keyId`，旧密钥确认停用后再删除。

## 13. HTTP 客户端实现要求

建议使用现有依赖中的 `httpx`：

- 复用连接池，但不要把维修密钥放在共享默认 headers 中。
- `trust_env=False`，禁止读取未知系统代理环境变量。
- 连接超时 10 秒、读超时 60 秒、写超时 60 秒、总超时 90 秒。
- 正式环境启用服务器证书校验和 mTLS：`cert=(client_cert, client_key)`。
- 只允许连接配置中的固定域名，禁止从 payload 指定 URL。
- 禁止自动跟随到非 HTTPS 域名的重定向。
- 日志只记录状态码、耗时、snapshotId、摘要和错误分类，不记录请求体。

## 14. Nginx 反向代理要求

云端建议使用独立域名 `sync.repair.example.com`：

```nginx
limit_req_zone $binary_remote_addr zone=v8_sync:10m rate=10r/m;

server {
    listen 443 ssl;
    server_name sync.repair.example.com;

    ssl_certificate     /etc/letsencrypt/live/sync.repair.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/sync.repair.example.com/privkey.pem;
    ssl_client_certificate /etc/nginx/v8-client-ca.pem;
    ssl_verify_client on;
    ssl_protocols TLSv1.2 TLSv1.3;

    location /api/integrations/v8/ {
        limit_req zone=v8_sync burst=5 nodelay;
        client_max_body_size 10m;
        proxy_pass http://127.0.0.1:8003;
        proxy_http_version 1.1;
        proxy_request_buffering on;
        proxy_connect_timeout 10s;
        proxy_read_timeout 90s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Client-Cert-Verified $ssl_client_verify;
    }

    location / {
        return 404;
    }
}
```

实际部署时：

- 接收服务只监听 `127.0.0.1:8003`。
- 8003、3101、3306、6379 不开放公网。
- 不暴露 FastAPI `/docs`、`/redoc`、`/openapi.json`。
- Nginx 只代理同步路径，禁止把整个后台服务暴露给采集端。
- 若使用 CDN/WAF，必须确认它不会剥离客户端证书校验或改变请求体；最简单的方式是同步子域名直连云服务器 Nginx。
- HMAC 验证仍由接收服务执行，不能把 mTLS 当成唯一鉴权。

## 15. 云端接收处理顺序

云端 `repair-v8-connection` 收到请求后按此顺序处理：

1. Nginx 完成 TLS 和 mTLS 客户端证书校验。
2. 接收服务限制请求大小和 gzip 解压大小。
3. 校验 clientId、keyId、时间戳、nonce、幂等键和 HMAC。
4. 校验 JSON Schema、计数和 `recordsSha256`。
5. 校验唯一键、日期、长度和跨表关系。
6. 把行数据写入 `v8_sync_snapshot_staging_*` 表。
7. 比较当前活动版本的机器数、绑定数和物料数。
8. 空快照或数量骤降超过阈值时进入人工确认，不自动覆盖。
9. 校验通过后，在一个事务中切换 `v8_active_snapshots` 指针。
10. 写入接收、发布或拒绝审计日志并返回结果。

云端绝不能执行请求体中的 SQL 字符串，也不能使用请求体中的表名拼接 SQL。所有写入使用服务端固定表名和参数绑定。

## 16. 环境变量

在 V8 `.env` 或专用服务配置中增加以下变量，真实值不提交：

```env
# 维修快照同步
REPAIR_SYNC_ENABLED=false
REPAIR_SYNC_BASE_URL=https://sync.repair.example.com
REPAIR_SYNC_CLIENT_ID=v8-factory-01
REPAIR_SYNC_KEY_ID=2026-01
REPAIR_SYNC_HMAC_SECRET=
REPAIR_SYNC_MTLS_CERT=
REPAIR_SYNC_MTLS_KEY=
REPAIR_SYNC_CA_BUNDLE=
REPAIR_SYNC_TIME=02:30
REPAIR_SYNC_TIMEZONE=Asia/Shanghai
REPAIR_SYNC_ALLOWED_CHECK_STATUS=manual_passed,passed,approved
REPAIR_SYNC_MAX_BODY_MB=10
REPAIR_SYNC_AUTO_ACTIVATE=true
```

开发环境先设置 `REPAIR_SYNC_ENABLED=false`，只执行 `snapshot` 生成和本地校验，不上传公网。联调时把 `REPAIR_SYNC_BASE_URL` 指向本地或测试域名，生产环境再启用正式证书和密钥。

不要复用：

```env
V7_API_KEY=
V8_SYNC_SECRET=
```

这两个变量属于现有业务，不应获得维修快照接口权限。

## 17. CLI 命令约定

建议提供以下命令，便于开发和运维：

```powershell
# 只从 V8 生成本地快照，不上传
python -m repair_sync snapshot --date 2026-07-16 --dry-run

# 生成当日快照并写入 outbox
python -m repair_sync daily

# 发送待上传和失败重试的快照
python -m repair_sync send-pending

# 查看最近快照和 outbox 状态
python -m repair_sync status

# 验证证书、域名、数据库只读权限和签名配置
python -m repair_sync verify-config
```

`daily` 成功生成后再 enqueue，不能先 enqueue 一个没有 payload 的事件。`send-pending` 失败时返回非零退出码，让 Windows 任务计划程序和日志系统能够发现失败。

## 18. Windows 自动任务

建议安装两个任务：

### 18.1 每日快照任务

```text
任务名：V8-Repair-Daily-Snapshot
时间：每天 02:30（Asia/Shanghai）
程序：项目虚拟环境中的 python.exe
参数：-m repair_sync daily
运行账号：V8 服务专用低权限账号
条件：无论用户是否登录都运行；网络可用后再启动
```

### 18.2 待发送重试任务

```text
任务名：V8-Repair-Snapshot-Retry
间隔：每 10 分钟
参数：-m repair_sync send-pending
```

如果 V8 API 本身稳定单进程运行，也可以让 `cloud_sync_worker_loop` 处理 `repair_snapshot_sync`；但仍建议保留第二个计划任务作为应用停止时的补偿通道。无论由哪个进程发送，必须使用相同的 outbox 事件和幂等键。

## 19. 重试和错误处理

| 情况 | 处理 |
|---|---|
| DNS、连接失败、超时 | 保留同一快照，按 1/5/15/30/60 分钟退避重试 |
| HTTP 408、429、500、502、503、504 | 使用同一幂等键重试 |
| HTTP 401、403 | 停止重试，提示密钥或证书失效 |
| HTTP 409 | 查询快照状态；若摘要相同标记成功，摘要不同则告警 |
| HTTP 422 | 数据契约或业务校验失败，停止自动重试，保留错误报告 |
| 本地 SQL/字段错误 | 不上传，标记快照 rejected，提示 V8 表结构变化 |
| 云端返回已激活 | 标记 outbox synced，不再次发布 |

错误日志必须包含 `snapshotId`、`businessDate`、`eventId`、错误类别和 HTTP 状态码，但不包含请求体、客户地址、OCR 原文、HMAC 或数据库密码。

## 20. 备份和保留

本地：

- 保留最近 7 天成功快照和最近 30 个失败报告。
- 快照目录 ACL 只允许运行账号访问。
- 日志按天轮转，默认保留 30 天。
- 上传成功后不能立即删除最后一个成功快照，至少保留一个应急回退版本。

云端：

- 保留至少 30 个成功快照和 180 天审计日志。
- 维修系统活动数据只通过版本指针切换，不能用 `TRUNCATE` 直接清空正式表。
- 数据库备份启用加密，备份不放在 Nginx Web 根目录。

## 21. 开发阶段

### 阶段一：本地快照生成

- 创建 `repair_sync` 包和本地快照表。
- 实现一致性查询、字段映射、白名单和摘要。
- 使用当前 V8 数据生成结果，与维修项目中的两份快照逐字段核对。
- 暂不上传网络。

验收：相同数据库状态下，重复生成结果摘要相同；敏感字段扫描无客户地址、OCR 原文和文件名。

### 阶段二：本地 outbox 和重试

- 增加 `repair_snapshot_sync` 事件类型。
- 实现每日业务键、锁和漏跑补偿。
- 模拟断网、V8 进程重启、重复执行 `daily`。

验收：每天只有一个快照事件；重复执行不会生成第二个业务快照；重试不改变 snapshotId。

### 阶段三：云端接收联调

- 在维修服务器部署 `repair-v8-connection` 测试实例。
- 配置 Nginx HTTPS 和测试 mTLS 证书。
- 联调 HMAC、nonce、幂等、Schema 和 staging 表。
- 验证云端只写入测试数据库。

验收：非法签名、过期时间戳、重复 nonce、修改请求体均被拒绝；合法快照可以暂存和发布。

### 阶段四：正式部署

- 为工厂创建独立 clientId、HMAC keyId 和 mTLS 证书。
- V8 MySQL 创建只读账号并限制来源 IP。
- Windows 计划任务以低权限账号运行。
- 云端先采用“上传后人工发布”，观察 3 天后再开启符合规则的自动发布。

## 22. 测试清单

### 数据正确性

- 新增机台、修改机型、绑定新零件后，次日快照包含正确行。
- 旧绑定失效后，云端 `active` 状态正确变化。
- 相同物料编码合并后，名称、类型和规格不冲突。
- `delivery_date` 正确进入保修起算字段。
- 配置项和机型关系正确，客户端只显示 `item_name`。

### 安全性

- 删除或修改 HMAC 请求体任意字节后请求失败。
- 重放相同 nonce 失败。
- 时间戳超过 5 分钟失败。
- 不带 mTLS 证书的请求在 Nginx 层失败。
- 只带原有 `V7_API_KEY` 不能调用维修快照接口。
- 上传 `customer`、`agent`、`file_name`、`recognized_value` 等字段时 Schema 拒绝。
- 公网无法访问 8003、3101、3306、6379。

### 可靠性

- 每日任务在 V8 停止时错过，恢复后能补跑。
- 上传中断后重试不生成重复快照。
- 云端校验失败不影响上一活动版本。
- 数量下降超过阈值进入人工确认，不清空维修资料。
- 云端数据库重启后可继续处理未完成快照。

## 23. 禁止的实现方式

- 禁止 V8 直接连接公网维修 MySQL。
- 禁止云端反向连接 V8 `rjfinshed`。
- 禁止上传拼接好的 `INSERT INTO ...` SQL 并让云端执行。
- 禁止把 `V7_API_KEY`、管理员密码或数据库密码写进脚本。
- 禁止把 HMAC 密钥打包进前端、桌面安装包可读资源或日志。
- 禁止只用 IP 白名单而没有 HTTPS 和请求签名。
- 禁止上传整行 `machine_component_bindings`，尤其是客户、代理商、OCR 和照片字段。
- 禁止收到快照后直接 `TRUNCATE` 维修系统正式表。
- 禁止对失败的 401、403、422 无限重试。

## 24. 完成标准

本地上传脚本完成后，应满足：

1. V8 每天自动生成一个完整的维修基础资料快照。
2. 快照数据可以明确映射到维修系统的 `machines`、`materials`、`material_instances` 和 `machine_material_bindings` 表。
3. 机型和维修物料配置可以随同快照发布，客户端只展示配置项名称。
4. 上传链路使用 HTTPS、mTLS、HMAC、时间戳、nonce 和幂等键。
5. 断网、重启和重复执行不会造成重复或半套数据。
6. 云端先暂存校验，再通过活动版本指针原子发布。
7. 失败、回滚、密钥轮换和人工确认都有审计记录。
8. V8 和维修云端均不提供任意 SQL 执行入口。

正式上线最低条件是：Nginx HTTPS、mTLS、HMAC、防重放、低权限 V8 只读账号、字段白名单、快照暂存、原子发布和回滚全部通过测试后，才能把 `REPAIR_SYNC_ENABLED` 改为 `true`。
