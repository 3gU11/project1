## 1. 背景与根因

### 1.1 数据链路

1. V8 后台定时调用云端 `GET /api/v8/bridge/orders?status=...&page=...&page_size=...`（HMAC 签名）分页拉取小程序订单，默认间隔 10 秒（`CLOUD_PULL_INTERVAL_SECONDS` 可调，最小 10 秒）。
2. 每拉到一条订单，V8 在 `crud/local_contract_drafts.py:create_from_order()` 里：
   - 把**整条原始订单 JSON** 原样存为快照（`source_snapshot`）；
   - 调用 `map_order_to_contract(order)` 生成订货单字段（存入 `fields_json`），其中明细会先按「规格型号 + 是否加高」把云端批次行合并（见 §2.4）；
   - 同一 `orderNo` + 同一快照内容只建一份草稿（重复拉取幂等）；订单内容变化时新建一版草稿。
3. 审批页面点「生成预览」时，`contract_bridge/renderer.py:render_order_form()` 读取模板 `contract_bridge/templates/dealer-order-form-v1.docx`，把值单元格里的 `{{字段}}` 占位符整体替换成字段值（缺失值替换为空串，**不会**把 `{{...}}` 漏到成品里）。
4. 审批通过后该 docx 会作为「合同附件」跟着转合同归档。

所以：**云端只需要在订单返回体里补上对应的字段值，V8 不需要改代码**；本文档的字段名、别名都是 V8 现成的取值规则（`FIELD_ALIASES` / `ITEM_ALIASES`）。

### 2.2 取值规则（云端必须知道）

- 除明细 `items[]` 外，**所有栏位只在订单顶层取值**：`settlementTerms`、`expectedDeliveryDate`、`customerAddress`、`officeName/officeBranch/officeContact/officePhone` 等**必须放在订单对象顶层**，放进 `items[]` 里不会生效。
- 每个栏位有一组别名，按列出顺序逐个匹配；**值为 null、空串、纯空白时视为「未提供」，继续看下一个别名**。因此新旧字段可以并存、逐步迁移。
- 所有值最终都以字符串形式写入草稿：拉单映射走 `_clean_text()`（`str(value).strip()`），审批页手工修改走 `update()`（`str(v or "")`）。因此云端传数字/布尔也会被转成字符串（例如布尔 `true` 会变成 `"True"`）。
- 纯整数的 Decimal 会去掉小数尾零：`"5.000"` → `"5"`（`_clean_text()`，`crud/local_contract_drafts.py:91-95`）。
- 明细的 `itemN_*` 编号是**合并后**的行号，不一定是云端 `items[]` 的数组下标（合并规则见 §2.4）；订单级栏位与明细行号互不影响。

#### 2.4.1 明细合并规则（V8 自动处理，云端无需聚合）

云端订单明细按批次行下发（同一型号可能拆成多行、每行 1 台）。生成订货单时，V8 会**先把明细合并，再逐行填表**：

- **合并键 = 规格型号 + 是否加高**：同型号同加高属性的行合并成一行，数量相加；合并后顺序按该键**首次出现**的顺序。
- **加高与普通分开**：同型号的普通机和加高机是两行，不会混在一起。
- **加高机型统一显示「（加高）」**：`FR-400XS(PRO)` 的加高机会显示成 `FR-400XS(PRO)（加高）`，便于审批人区分。
- **没有规格型号的行不参与合并**：原样各占一行，避免把不同设备误并成一行。
- **数量相加**：用 Decimal 相加（`"1.000"` + `"1.000"` → `"2"`）；任一侧为空或不是数字时保留原值、不丢数据；两行都没有数量时保持空白（不按 0 相加）。
- **产品名称 / 税票**：合并行取组内第一个非空值；都没有时产品名称按 §2.4 默认规则补、税票默认「含税」。

加高判定方式（只看明细自身字段）：`items[].inventoryType`/`inventory_type` 取值属于 `heightened`、`heighten`、`high`、`tall`，**或**规格型号里已含「加高」（含「(加高)」「（加高）」）。**不看订单 `remark`**——云端会把订单备注复制到每一行，按备注判断会把整单误标成加高（详见 §3.7、§7）。

示例（真实订单 `DO179282289112342793C`，云端 8 条批次行 → 订货单 4 行明细，且不再自动加行、整张单回到 1 页）：

| 云端 `items[]` 批次行（8 行） | 合并后订货单明细（4 行） |
| --- | --- |
| FH-300C ×1（finished）、FH-300C ×1（wip） | FH-300C，数量 **2** |
| FR-400G ×1（finished）、FR-400G ×1（wip） | FR-400G，数量 **2** |
| FR-400XS(PRO) ×1（finished）、FR-400XS(PRO) ×1（wip） | FR-400XS(PRO)，数量 **2** |
| FR-400XS(PRO) ×1（heightened）、FR-400XS(PRO) ×1（heightened） | FR-400XS(PRO)（加高），数量 **2** |

## 3. 云端需改造清单（按优先级）

> 建议排序依据：P0 是本次「交货时间/结算方式空白」的直接原因且云端表单已有数据源；P1 是用户当前最想要的办事处信息（全部可选）；P2 是后期优化；税票可不改。

### 3.1 P0-1 期望交期 → `expectedDeliveryDate`

| 项目 | 内容 |
| --- | --- |
| 云端表单位置 | 「客户信息」区块 →「期望交期」（日期选择器，占位 `yyyy/mm/日`） |
| 建议返回字段 | 订单顶层 `expectedDeliveryDate`，字符串。建议格式：`2026-11-20` 或原样中文 `2026 年 11 月（具体等客户通知）` |
| 兼容写法 | 也可以直接填充**现有** `deliveryDate`（V8 也认，但 `expectedDeliveryDate` 优先级更高，两者都存在时以后者为准）；下划线 `expected_delivery_date`、中文 `期望交期`/`交期`/`交货时间` 同样认 |
| 注意 | 必须放**订单顶层**，不要只放在 `items[]` 里 |
| 未提供时 V8 兜底 | 交货时间留空，不阻断审批，审批人可在「编辑字段」里补 |

### 3.3 P1 办事处信息（4 个字段，全部可选）

> 用户明确：「现在所需的就是办事处信息，但非必填」。这 4 个字段**不参与缺项校验**，不传不影响审批，只是留空；审批人可在「编辑字段」里补。

| 字段 | 建议返回字段（订单顶层） | 类型/格式 | 映射到订货单 | 未提供时 V8 行为 |
| --- | --- | --- | --- | --- |
| 所属办事处 | `officeName` | 字符串（如 `浙江办`） | 第 2 行「所属办事处」 | 留空，不阻断审批 |

补充说明：

- 云端订单表单截图（2026-10-24）只看到「客户信息」区块，**未见**办事处信息输入项。建议在「客户信息」区块之后新增「办事处信息」4 个可选输入，由下单人或办事处在表单里**如实填写**；不要把「所属大区经理」自动当成办事处联系人（V8 已去掉这层兜底，不会再拿大区经理顶替）。

| 兼容写法 | 地址也认 `customer_address`、`buyerAddress`、`deliveryAddress`、`address`、中文 `客户地址`/`地址`/`收货地址`/`交货地址` |

### 3.5 税票：可不改（V8 已默认「含税」）

- 云端表单（2026-10-24 截图范围内）没有税票字段，**不改也能出单**：V8 对**订单实际有的每一条明细行**默认填「含税」（`DEFAULT_TAX`）。
- 模板里空着的第 3、4 行明细保持空白，不会写「含税」；「含税」只出现在订单实际有的明细行上。边界情况：如果订单连 `items` 都没有，V8 会把订单本身当成第 1 行明细，此时第 1 行税票仍会写「含税」（其余栏位空白）——正常订单都会带 `items`，不影响。
- 如需覆盖，建议在 `items[]` 每条明细里传 `taxIncluded`（字符串）：`"含税"` / `"不含税"`；也认 `tax`、`tax_included`、`invoiceType`、`taxType`、中文 `税票`。
- **注意**：不要传布尔 `true/false`。V8 会把值直接转成字符串，布尔值会在税票栏渲染成 `"True"` / `"False"`；传字符串才符合业务语义。

### 3.6 可选补充（后期）

| 字段 | 建议返回字段 | 说明 |
| --- | --- | --- |
| 其他特殊要求 | `specialRequirements`（或沿用 `extraRemark`） | 云端表单暂无对应框；不传则该栏留空。纸质样张中的「收货信息直接写办事处信息」属于此类内容 |
| 实际签订时间 | `signedDate` | 现在靠 `createdAt` 兜底，显示的是下单时间；若业务需要区分「实际签订日期」，建议单独提供，V8 会格式化成「2026 年 10 月 23 日」 |

### 3.7 加高机型标识（无需改动，保持现状即可）

V8 已能识别两种加高标识，云端**保持其中一种**即可，不需要新增字段：

| 云端做法 | 示例 | V8 行为 |
| --- | --- | --- |
| 明细 `inventoryType` 标加高（推荐，当前已在下发） | `"inventoryType": "heightened"`（也认 `heighten`、`high`、`tall`） | 判为加高，规格型号后统一显示「（加高）」 |
| 机型后缀直接带「加高」 | `"model": "FR-400XS(PRO)（加高）"` 或 `"(加高)"` | 同样判为加高，并规整成「型号（加高）」显示 |

补充：

- **明细继续按批次行/逐台下发即可**（同一型号多行、每行 1 台），V8 会自己按「型号 + 加高」合并数量；云端**不需要**为了订货单去聚合明细。若云端本来就按型号聚合下发（每行 `quantity: 2`），V8 也会正常显示。
- **不要把「加高」只写在订单备注里**：V8 的加高判定只看明细自身的 `inventoryType` 或规格型号，不看订单 `remark`（云端会把订单备注复制到每一行，用备注判断会把整单误标成加高）。
- 若同一型号同时有普通机与加高机，务必让两者在明细上可区分（`inventoryType` 或型号后缀），否则 V8 无法拆成两行。

## 5. 兼容与影响面

| 事项 | 结论 |
| --- | --- |
| 字段名兼容 | 每个栏位同时认驼峰、下划线、中文别名（见 §2）；旧字段名继续可用，新旧可并存，云端可以渐进迁移 |
| 是否要改 V8 代码 | 不需要。上表别名已在 `FIELD_ALIASES` / `ITEM_ALIASES` 中，云端按推荐字段名传值即生效 |
| 已生成的草稿 | 云端后续改字段不会改写已存在草稿：草稿的 `fields_json` 在创建时生成；同一订单快照重复拉取幂等，**订单内容变化时才新建一版草稿**，旧版保留可追溯（本次映射规则升级前生成的存量草稿例外，读取时会被规整，见下一行） |
| 旧草稿（换模板前的「订货合同」字段集） | 读取时 `_upgrade_legacy_fields()` 会用当时的订单快照重算新字段集，旧值里非空的覆盖上去（防止冲掉审批人改过的内容）；旧字段集里**为空**的旧键（`contract_no`、`item1_price` 等）不再出现，但**非空**的旧键会被原样保留（见 §7 第 7 条） |
| 存量草稿规整（本次映射规则升级前生成） | `get()` 读取时按当前规则规整，**不写库**，返回给页面的已是规整后的字段：① **有产品名称或规格型号但税票为空**的明细行补默认「含税」；② 签订时间 ISO 日期转「2026 年 10 月 24 日」；③ 明细逐行存的旧草稿在**数量口径没被人工改过**时按「型号 + 加高」合并重排；④ 加高机型补「（加高）」标记；⑤ 旧草稿里用大区经理兜底写进去的办事处联系人清空（等云端补 `officeContact`）；⑥ 按订货单栏位顺序重排字段。**审批人人工改过数量/型号的（按型号汇总数量与订单快照对不上）保持原样，不覆盖。** |
| 旧预览自动作废 | 若规整后的字段与库里 `fields_json` 不一致且草稿状态是 `preview_ready`，`get()` 返回的 state 变为 `submitted`、`preview_hash` 置空（不写库）——审批页打开时会按新字段重新生成预览，避免对着旧版附件审批归档；`prepare()` 生成预览时会把规整后的字段一并落库，所以不会反复被判过期。 |
| 已归档合同 | `approved` 状态不会被作废重生成：返回状态仍是 `approved`，历史预览与归档附件不变；读取时也不再按新规则规整字段（展示口径与归档时一致），保证页面字段和已归档附件对得上；不可再编辑 |
| 缺项校验 | `REQUIRED` 仍为 4 项：`supplier_name`、`dealer_name`、`signed_date`、`buyer_name`。办事处信息、地址、交货时间、结算方式、税票、其他特殊要求**都不参与校验**，缺失不阻断审批，审批人可在页面上补 |
| 空白栏位处理 | 字段缺失渲染为空串，不会在 docx 里残留 `{{占位符}}`；需求方在预览里看到空白栏位后可在「编辑字段」补齐再审批 |
| 明细行数 | **按合并后行数**计：最少 4 行（模板自带，少的留空），最多 30 行；合并后超过 4 行自动复制模板行加行。示例：云端 8 条批次行 → 合并成 4 行，明细区正好用满模板 4 行、不再加行。 |
| 数值/日期格式 | 数量 `"5.000"`→`"5"`；签订时间 ISO 日期转中文日期「2026 年 10 月 23 日」，非 ISO 自由文本原样保留 |
| 审批页编辑顺序 | 订单头 → 明细行 → 备注/交货时间/结算方式 → 购货方信息 → 办事处信息 → 其他特殊要求（前端 `ContractDraftReview.vue` 的字段标签与顺序） |

## 7. 已知差异与待确认（复核代码发现，本次只报告、不修改代码）

1. **办事处联系人已去掉大区经理兜底**（2026-10-24 按业务要求调整）：`office_contact` 只认云端 `officeContact`，未提供时留空，订货单第 16 行「办事处 联系人」不再显示所属大区经理。旧草稿里之前被兜底写入的大区经理名字，读取时会被清空并触发预览重生成。云端补 `officeContact` 后正常带出（纸质样张是「俞文涛」）。
2. **明细按「规格型号 + 是否加高」合并，`items[]` 粒度不再影响行数**：同型号的多条批次行会合并成一行、数量相加，所以云端一行一机型或一行一批次下发都可以，不需要为订货单聚合。需要注意两点：① 加高判定只看明细自身字段（`inventoryType` ∈ `heightened`/`heighten`/`high`/`tall`，或规格型号含「加高」），**不看订单 `remark`**——云端会把订单备注复制到每一行，按备注判断会把整单误标成加高；② 同型号若同时有普通机与加高机，云端必须让两者在明细上可区分（`inventoryType` 或型号后缀），否则 V8 无法拆成两行。
3. **`taxIncluded` 不要传布尔值**：V8 会把值直接转字符串，布尔 `true/false` 会渲染成 `"True"`/`"False"`。税票栏应传字符串「含税」/「不含税」；`invoiceType`（如「增值税专用发票」）同样会原样显示在税票栏。
4. **非明细字段必须在订单顶层**：`settlementTerms`、`expectedDeliveryDate`、`customerAddress`、`office*` 若只放在 `items[]` 里，订货单对应栏位不会带出（订单级映射只读订单对象）。
5. **签订时间目前是「下单时间」**：云端没有独立的签订时间字段，`createdAt` 兜底后显示为下单/创建时间；若业务上「签订时间」指实际签约日期，需要云端补 `signedDate`（`submitTime` 也会被当作签订时间）。
6. **云端表单截图范围有限**：2026-10-24 提供的截图只覆盖「客户信息」区块，未见到「所属办事处/办事处信息/税票/其他特殊要求」的输入项；若这些字段已在表单其他位置存在，请直接把值补进返回体，无需新增录入界面。另：客户信息/地址当前是一栏，拆分前购货方名称栏可能显示「客户 + 地址」整串。
7. **旧草稿升级会保留非空的旧键**：`_upgrade_legacy_fields()` 以新字段集为底，再把旧草稿里**非空**的值逐个覆盖上去。旧字段集里为空的键（测试用的 `contract_no`、`item1_price`）会被清掉，但**有值**的旧键（如 `contract_no`、`total_upper`、`item1_price`、`item1_brand`）会被保留进新字段集。订货单模板不引用这些键，渲染不受影响；但审批页「编辑字段」若把草稿字段全量展示，可能出现无中文标签的旧字段。本次按要求只报告，未改代码。
