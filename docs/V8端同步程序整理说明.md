# V8 端同步程序整理说明

> 适用目录：`D:\CURSORpj\V8BetaV1.1`
>
> 文档依据当前代码整理，范围是 V8 与订货小程序 API 之间的订货、库存和机型目录同步。

## 1. 总体结构

V8 启动 FastAPI 时会创建四类后台任务：

```text
api/main.py
  ├─ cloud_sync_worker_loop      V8 -> 云端：处理 outbox 事件
  ├─ cloud_pull_worker_loop      云端 -> V8：拉取经销商订单
  ├─ watch_dealer_orders_db      V8 本地订单表变化通知 WebSocket
  └─ watch_finished_goods_db      V8 库存变化/定时快照入队
```

这四条任务职责不同：

| 任务 | 方向 | 作用 | 当前频率 |
|---|---|---|---:|
| `cloud_sync_worker_loop` | V8 -> 云端 | 消费 `cloud_sync_outbox`，上传快照或回写订单状态 | 每 5 秒检查一次 |
| `cloud_pull_worker_loop` | 云端 -> V8 | 分页拉取小程序订单，写入 V8 `dealer_orders` | 默认每 10 秒 |
| `watch_dealer_orders_db` | V8 内部 | 订单表变化后推送待审核数量 WebSocket | 每 1 秒 |
| `watch_finished_goods_db` | V8 内部 | 发现库存变化或到达定时点时创建库存快照事件 | 每 2 秒检查 |

## 2. 同步的数据边界

### 2.1 V8 提供给小程序端的数据

库存快照由以下 V8 数据生成：

- `finished_goods_data`：逐台成品源数据；
- `wechat_batch_summary`：由 V8 根据待入库、库存中数据汇总的订货读模型；
- `model_dictionary`：启用状态、机型系列和排序。

上传的快照包含：

```text
schemaVersion
snapshotId
generatedAt
rows[]       // 批次、预计入库时间、机型、数量、加高标记
models[]     // 机型、系列、排序、启用状态
```

`finished_goods_data` 的逐台流水不会直接上传。`factory_plan` 也不作为库存快照整表上传；V8 审核订单时可能在本地合并批次和客户信息到 `factory_plan`，这属于 V8 内部业务写入，不等于 Bridge 同步。

### 2.2 小程序端提供给 V8 的数据

小程序端的 `dealer_orders` 是订单主数据。V8 按订单状态分页拉取后，镜像到 V8 本地 `dealer_orders` 表。

V8 保留本地已经推进的较高状态，避免一次拉取把工厂已审核、已合同或已配货的状态覆盖回较低状态。订单行以 `(order_no, line_no)` 去重；使用 `status=all` 同步时，还会清理云端已经删除且此前因 404 留下的本地旧行。

### 2.3 V8 回写小程序端的数据

V8 的工厂操作会生成 outbox 事件，再回写小程序订单：

| 事件 | 典型触发 | 云端状态 |
|---|---|---|
| `dealer_order_reviewed` | 审核通过/驳回 | `approved` / `rejected` |
| `dealer_order_contracted` | 转合同 | `contracted` |
| `dealer_order_allocated` | 工厂配货 | `allocated` |
| `dealer_order_completed` | 订单完成 | `completed` |

## 3. 库存和机型快照流程

```text
finished_goods_data
        │
        ├─ 每 2 秒检查 MAX(更新时间)、COUNT(*)
        │       └─ 发生变化：入队 wechat_batch_summary_sync
        │
        └─ 默认每 300 秒：入队 scheduled_snapshot
                    │
                    ▼
          cloud_sync_outbox（pending）
                    │ 每 5 秒消费
                    ▼
       refresh_local_wechat_batch_summary()
                    │
                    ▼
       POST /api/v8/bridge/snapshot
```

快照在 V8 端先重建 `wechat_batch_summary`，再读取汇总行和 `model_dictionary` 生成 `snapshotId`。小程序 API 端会校验摘要、HMAC、时间戳和 nonce，并以事务方式替换云端读模型。

库存全量快照的配置是：

```dotenv
V8_ORDERING_SNAPSHOT_INTERVAL_SECONDS=300
```

它不是订单拉取频率。库存数据库变化仍由 2 秒检查器发现并即时入队，outbox 再负责上传和重试。

## 4. 订单拉取流程

```text
小程序 dealer_orders
        │
        ▼
GET /api/v8/bridge/orders
  status=pending/approved/contracted/partial_allocated/
         allocated/completed/rejected/cancelled
        │ 分页、HMAC
        ▼
sync_cloud_dealer_orders("all")
        │
        ▼
V8 dealer_orders
```

当前默认配置：

```dotenv
ENABLE_CLOUD_PULL=true
CLOUD_PULL_INTERVAL_SECONDS=10
```

代码将最低间隔限制为 10 秒。每轮会并发读取 8 种订单状态；每种状态默认最多读取 20 页、每页最多 100 条，因此正常情况下每轮约 8 个请求，达到分页上限时最多约 160 个请求。云端负载较高时，可以把 `CLOUD_PULL_INTERVAL_SECONDS` 调大；不能通过降低库存快照间隔来替代订单拉取间隔。

## 5. 工厂状态回写和 outbox

工厂审核、转合同、配货等事务在本地订单更新时，同时写入 `cloud_sync_outbox`。后台 worker 每次最多处理 20 条事件：

```text
dealer_orders 事务
      └─ cloud_sync_outbox（pending）
                │
                ├─ 成功：synced
                └─ 失败：failed + next_retry_at
                              │
                              └─ 到期后重试
```

非维修同步事件的重试间隔为：30 秒、2 分钟、5 分钟、之后每 10 分钟一次。事件使用 `event_id` 作为 `Idempotency-Key`，云端重复收到同一事件时不会重复推进业务状态。

当前 outbox 事件类型还包含 `repair_snapshot_sync` 和 `repair_delta_event_sync`。它们属于维修系统同步，不属于订货 Bridge；本说明只列出它们是为了避免把 outbox 表误认为只有订单事件。

## 6. Bridge HTTP 接口

### 6.1 V8 调用订货小程序 API

```text
GET  /api/v8/bridge/orders?status=...&page=...&page_size=...
POST /api/v8/bridge/snapshot
POST /api/dealer/orders/{orderNo}/v8-status
```

### 6.2 V8 本地管理接口

V8 路由前缀为 `/api/v1/dealer-orders`：

```text
POST /api/v1/dealer-orders/sync-cloud
POST /api/v1/dealer-orders/sync-wechat-batch-summary
GET  /api/v1/dealer-orders/cloud-sync-status
POST /api/v1/dealer-orders/cloud-sync-retry
POST /api/v1/dealer-orders/sync-completed-cloud
```

这些接口用于人工触发、查看失败事件和补偿同步，不替代后台 worker。

## 7. HMAC 安全要求

V8 和小程序 API 必须配置同一个高熵密钥：

```dotenv
V8_SYNC_SECRET=至少 32 字节的随机密钥
```

签名覆盖时间戳、nonce、HTTP 方法、请求路径、POST 的 `Idempotency-Key` 和原始请求体摘要。服务端会拒绝超过 5 分钟的时钟偏差和重复 nonce，因此两台服务必须校准系统时间。

签名规范串按以下顺序拼接，各字段之间使用换行符；GET 的 `Idempotency-Key` 字段为空：

```text
timestamp\nnonce\nHTTP_METHOD\nrequest_path\nIdempotency-Key\nsha256(raw_request_body)
```

签名算法为 HMAC-SHA256，头部格式为 `X-V8-Signature: sha256=<hex digest>`。

库存快照默认拒绝空库存；只有业务上确实要清空云端库存时，才显式配置：

```dotenv
V8_BRIDGE_ALLOW_EMPTY_INVENTORY=1
```

## 9. 启动和排查顺序

1. 在 V8 根目录 `.env` 配置 `WECHAT_CLOUD_API_BASE`、`V8_SYNC_SECRET` 和数据库参数。
2. 启动 `run_fullstack.ps1`，确认 FastAPI 监听配置的 8000 端口。
3. 查看日志中是否出现 `cloud pull worker started` 和 `cloud sync worker started`。
4. 用 `GET /health` 确认 V8 API 存活。
5. 用 `GET /api/v1/dealer-orders/cloud-sync-status` 查看 `pending`、`failed` 和最近失败原因。
6. 先人工触发一次库存同步，再验证小程序端库存和机型目录。
7. 新建测试订单，确认 V8 能在一个拉取周期内出现；再执行审核/配货，确认 outbox 变为 `synced` 且小程序订单状态回写。

## 10. 当前环境结论

- 代码默认订单拉取间隔已为 10 秒，库存全量快照默认仍为 300 秒。
- 当前 V8 `.env` 有 `WECHAT_CLOUD_API_BASE=http://127.0.0.1:8787`，但本次检查未发现 8787 监听服务。订货小程序 Node API 源码默认端口是 8001，部署时应核对目标地址和实际监听端口；不要直接假设生产端口也是 8001。
- 当前 V8 `.env` 未配置 `V8_SYNC_SECRET`，订货 server 目录也没有本地 `.env` 文件。若进程环境未另行注入同一密钥，签名订单拉取、库存快照和状态回写都会失败，这是配置/联调条件不足，不是轮询逻辑故障。
- 已有协议单元测试和 Python 编译检查通过；真实云端数据库、HMAC 密钥和完整订单往返仍需在两端服务启动后做一次联调验收。
