# 工作流执行租约死锁复盘与优化方案

- 日期：2026-11-20
- 范围：移动端入库员批量入库触发的 MySQL 1213 死锁
- 涉及表：`workflow_instances`、`workflow_execution_attempts`、`workflow_object_locks`、`workflow_business_receipts`
- 相关代码：`frontend-mobile/src/views/InventoryQuery.vue`、`api/routes/workflows.py`、`crud/workflows.py`、`crud/forward_entries.py`

## 1. 事件回顾

| 时间 | 操作 | 实例 | 结果 |
| --- | --- | --- | --- |
| 17:16:27 | 移动端多选入库 3 台 | 64、65、66 | 64 成功，65、66 死锁 |
| 17:19:35 | 移动端多选入库 9 台 | 74–82 | 74、75 成功，76–82 死锁（截图中的 id 80 在内） |

- 9 个死锁请求全部返回 `500 逆向流程提交失败：... (1213, Deadlock found ...)`；
- 9 个实例停在 `已通过`，`workflow_object_locks` 仍为 `占用中`；
- 对应 9 台机台保持 `待入库`，入库员重试会得到“业务对象已被其他流程占用”；
- 该批机台目标库位均为“一楼二车间小机”（容量 100，当时只占 3 台）。

## 2. 根因

### 2.1 调用链

移动端一次点击多选“确认入库”：

1. `InventoryQuery.vue confirmInbound` 把选中的 N 台机台用 `Promise.allSettled` 同时发出 N 个请求；
2. 每个请求走 `POST /inventory/inbound-to-slot` → `submit_entry` → `submit_reverse_instance`；
3. 每个请求独立创建一条 `stock-inbound` 实例（`已通过`），并立即抢执行租约；
4. `acquire_execution_lease` 先查有没有“执行中”的租约，没有就插入一条 `workflow_execution_attempts`。

### 2.2 锁图

`workflow_execution_attempts` 的唯一键是 `uq_workflow_attempt_no(instance_id, attempt_no)`。

修复前查询租约使用了 `SELECT ... FOR UPDATE`。对新实例来说这一行不存在，而新实例 ID 又大于表中已有最大 ID，于是：

```text
T1：锁实例 75 行 → SELECT 租约 FOR UPDATE → 对 uq_workflow_attempt_no 的 supremum 加 next-key X 锁
T2：锁实例 82 行 → SELECT 租约 FOR UPDATE → 对同一个 supremum 加 next-key X 锁
T1：INSERT workflow_execution_attempts(75,1) → insert intention 等 T2 的间隙锁
T2：INSERT workflow_execution_attempts(82,1) → insert intention 等 T1 的间隙锁
→ 1213 死锁，MySQL 回滚 T2
```

两个事务持有的实例行不同，唯一共享资源就是这条唯一索引尾部的间隙锁；因此这是“首次插入并发”死锁，不是库存行锁冲突。

### 2.3 为什么是首次租约、为什么是移动端

- 受害者全部 `attempt_no = 1`：只有首次租约才需要插入空行；已有租约时查询会锁到真实行。
- 新实例 ID 总在表尾，所有并发首次租约都落在同一个 supremum 间隙。
- PC 端 `Inbound.vue` 使用 `for ... await` 串行提交，第一台提交完成后第二台才查询，不会出现同窗口并发。
- 移动端 `Promise.allSettled` 把 N 个请求同时发出，窗口完全重叠。

### 2.4 现场证据

- MySQL `SHOW ENGINE INNODB STATUS`：2026-11-20 17:19:35，事务 14083590（实例 75）与 14083597（实例 82）互等，均持 `uq_workflow_attempt_no` supremum X 锁、均等 insert intention，回滚事务 2。
- API 日志：9 次 1213，全部栈在 `api/routes/workflows.py:353 acquire_execution_lease` → `crud/workflows.py` 的 `INSERT workflow_execution_attempts`。
- 数据库：9 个实例 `已通过`、9 条对象锁 `占用中`、9 台机台 `待入库`，17:19 之后无新的 `stock-inbound` 实例。

## 3. 并发事件判定

并发来自**同一次移动端批量入库提交内部**，不是多用户、重复点击或后台任务：

- 9 个实例的 `initiator_id` 都是同一入库员；
- 9 个实例创建时间精确到同一秒；
- 9 个实例 ID 连续，业务对象是 9 台不同机台；
- 租约首次插入只发生在提交入口，排产/同步任务不会创建 `stock-inbound` 租约。

## 4. 已实施修复

| 修复项 | 内容 | 文件 |
| --- | --- | --- |
| 租约判据改到实例行 | 保留 `workflow_instances` 行锁串行化，去掉租约空行的 `FOR UPDATE`，消除 supremum 间隙锁 | `crud/workflows.py` |
| 1213 重试 | 整段租约事务回滚后重试，最多 3 次，避免只重试单条 INSERT | `crud/workflows.py` |

| 回归测试 | 租约重试、回执无锁、失败释放、路由清理 | `tests/test_workflow_lease_deadlock.py`、`tests/test_workflow_deadlock_recurrence.py` |

## 5. 剩余风险

1. `workflow_execution_attempts` 同时承担“执行历史”和“当前租约状态”，职责混合，后续仍可能出现“先查后插”类竞态。
2. `execute_forward_entry` 的“建实例 → 抢租约 → 执行业务 → 写回执”跨多个事务；业务成功后回执/收尾失败时，仍需人工确认。
3. `ensure_workflow_tables()` 每个请求执行一批 `CREATE TABLE IF NOT EXISTS` 与 `SHOW COLUMNS`，并发时增加元数据锁和延迟。
4. 移动端只做了串行提交，没有服务端批量接口；网络重试/重复点击仍可能产生重复实例。
5. 缺少 1213 的按阶段监控与自动告警；`close-stale` 没有定时任务，只能人工调用。
6. 没有真实 MySQL 的并发回归测试；当前单元测试只验证代码路径与重试逻辑。

## 6. 优化方案

### P0（本次已完成）

- 修复租约间隙锁死锁与 1213 重试；
- 修复业务回执同构死锁；
- 抢租约失败自动释放实例与对象锁；
- 移动端批量入库串行化；
- 清理 9 个残留实例。

### P1（短期，建议下一迭代）

1. **拆分“租约状态”和“执行历史”**
   - 新增 `workflow_instance_leases(instance_id PK, worker_id, lease_token, lease_expires_at, status)`；
   - 建实例时同步创建租约行（一定存在），抢租约改为对该行做条件 `UPDATE`；
   - `workflow_execution_attempts` 只追加历史，不再参与判属。
2. **提供批量入库接口**
   - `POST /inventory/inbound-batch` 在一个请求内按顺序处理多台，返回逐台结果；
   - 移动端一次只发一个请求，彻底消除客户端并发窗口。
3. **幂等加固**
   - 以 `业务类型 + 业务对象 + 批次号` 生成稳定幂等键；
   - 服务端对重复键返回“已受理”，而不是新建实例。
4. **自动清理**
   - 定时调用 `close-stale`（或新增 `release_unstarted_instance` 的定时扫描）；
   - 超时未执行的 `已通过` 实例自动释放对象锁。
5. **可观测性**
   - 1213/1205 按 `stage`（create/lease/execute/finalize）计数；
   - 记录 `instance_no`、`attempt_no`、`worker_id`、`error_code`；
   - 死锁次数、锁等待时间、租约回收量进入监控告警。
6. **初始化缓存**
   - `ensure_workflow_tables` 进程内只执行一次，或引入 `schema_migrations` 版本表。

### P2（中期，结构性）

1. **统一执行协议**
   - 定义 `claim（原子抢租约）→ execute（业务）→ finalize（回执/状态）` 三阶段；
   - 每阶段幂等，任一步失败都能安全重试；
   - 业务执行前先写“执行中回执”，成功后更新，失败保留可核查状态。
2. **隔离级别评审**
   - 工作流事务可评估 `READ COMMITTED`（消除间隙锁），但必须同时用唯一键/原子 UPDATE 保证判属，不能只依赖隔离级别。
3. **并发测试基线**
   - 增加真实 MySQL 集成测试：两个连接并发抢同一实例 / 不同新实例，断言无 1213、租约唯一；
   - 默认跳过，CI 用独立 schema 执行。
4. **模型层约束**
   - 对“查询不存在行再插入”的仓库方法做静态检查或代码评审清单；
   - 所有 `FOR UPDATE` 必须说明锁的对象是否一定存在。

## 7. 验收标准

- 移动端一次选择 20 台入库，服务端串行处理后全部成功，无 1213；
- 并发提交同一台机台，只有一个实例拿到租约，其余返回“已有流程占用”或幂等结果；
- 抢租约失败/执行失败的实例在 1 分钟内自动释放对象锁，可再次入库；
- 监控能看到 1213 的阶段分布，且连续 7 天为 0；
- 真实 MySQL 并发集成测试稳定通过。
